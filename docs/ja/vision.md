# 今後の方向性：レポートからコンポーザブルなデータへ

最終更新：2026-11-22。本ページは、MAD が成長していくために設計された方向性を示すものです。現在出荷されているものと提案中のものを区別し、内部の作業メモではなく公開された設計記録——[データオブジェクトの設計](developers/data-object.html)、[マルチソースレポート](developers/multi-source.html)、[フォーマット仕様](README.html)——を参照します。

## 現在存在するもの

`.mad` ドキュメントはレポートの**定義**です。すなわち、スキーマスナップショット、クエリグラフ（テーブル、結合、述語、グループ化）、およびバンド型レイアウトツリーです。更新（リフレッシュ）時には、エンジンがグラフを SQL にコンパイルし、行を一度だけ読み取って、コンパニオン SQLite キャッシュ（`.maddb` + `.mdcache`）にマテリアライズします。行データは意図的にドキュメントの外に置かれ、定義は 100 KB 未満に保たれます。

エンジンには、より広い方向性に必要な部品がすでに揃っています：

* オープンでポータブルなドキュメントフォーマット：ポータブルな SQLite ストアを格納した bzip2 tar アーカイブで、開くために Apple フレームワークを必要としません。
* 構造化された定義を SQL にコンパイルするクエリビルダーに加え、直接入力されたステートメント用の SQL パーサー。
* 4つの SQL ドライバ——MySQL、SQL Server、PostgreSQL、SQLite——があり、それぞれスキーマと行をテーブルとして返します。
* ローカル SQLite マテリアライズ（`MADDataTableFast`）により、グループ化、集計、および繰り返しレンダリングがスマートフォン上でも実用的になります。
* ネイティブな iOS および macOS アプリケーション、ネイティブな Windows アプリケーション、そして `mad serve` と `mad` CLI を通じて Linux および Windows 上でヘッドレスに動作する同じエンジン。

見落としやすい帰結が一つあります：**レポートとはデータソースからテーブルへの関数である**ということです。すべてのドライバはスキーマと行をテーブル形式で返し、レポートの出力もまたスキーマと行をテーブル形式で*そのまま*表したものです。エンジンはすでにこの両者を同一に扱っています。

## 目指す方向

以下の方向性は提案です。それらは上記のアーキテクチャの上に構築されますが、本ページがそう述べていない限り、今日出荷されているものはありません。

### コンポーザブルなデータオブジェクト

データベースでは、`employee` や `sales_data` のようなベーステーブルから選択します。レポートは複数のテーブルを結合し、その出力はアドホックにマテリアライズされた SQLite テーブルです。今日では、クエリを別のレポートの出力に向けることはできません。結果キャッシュは存在しますが、アドレス指定可能な識別子ではなくファイル名のハッシュをキーとしているためです。

その出力に安定した識別子を与えれば、あるレポートの結果を、他のレポートが選択したり結合したりできるテーブルにできます。レポートの上に構築されたレポートは、派生テーブルの有向非巡回グラフ（DAG）となり、レポートを設計することがそのまま再利用可能なデータソースを設計することになる、ポータブルなセマンティックレイヤーとなります。[データオブジェクトの設計](developers/data-object.html)では、そのモデルと、それを正式化するために必要なものを説明しています。

### マルチソースのローカルマテリアライズ

すべてのドライバは、その結果セットを同じローカル SQLite テーブル表現にマテリアライズします。1つのドキュメントが複数のクエリ定義を保持し、それぞれの出力をテーブルとして参照できるようになれば、1つのレポートで PostgreSQL のテーブルを SQL Server のテーブルに、さらに MySQL のテーブルに結合できます——中間にフェデレーションサーバーを置くことなく、SQLite 上でローカルに統合されます。各ソースは自身のデータを理解し、MAD は結果として得られるテーブルを理解します。[マルチソースの設計](developers/multi-source.html)では、アーキテクチャとフェーズを記録しており、すべてが構築済みというわけではありません。

### 組み込みおよびヘッドレスでの利用

MAD は MAD という名前のアプリケーションに限定される必要はありません。同じエンジンを他の開発者の製品に組み込むことができます。たとえば、在庫管理システム、金融アプリケーション、製造ツール、または、レポーティングサブシステムをゼロから構築することなくクエリ、レポート、エクスポート、および運用サマリーを必要とする業界固有の管理システムなどです。

ホストアプリケーションは、データアクセス、統合、および独自のユーザー体験を提供します。MAD は、再利用可能なクエリ、マテリアライズ、レポーティング、およびエクスポートの機能を提供します。ドライバの接合部（シーム）は意図的に広く設計されています——ソースはスキーマと行を提供する必要があり、必ずしも従来型の SQL データベースである必要はありません——そのため、同じ契約でリレーショナルデータベース、ローカルアプリケーションデータ、構造化ファイル、およびデバイスに対応できます。これらのソースの一部には今日ドライバがありますが、他のものにはドライバが必要になるでしょう。

この方向性はデスクトップソフトウェアの枠を超えても広がります。十分なリソースを持つアプライアンスや産業システムは、エンジンをローカルで使用して、測定値や保守記録を診断レポートに変換できます。継続的な接続は必要ありません。ただし、これは完全なエンジンが小さなマイクロコントローラーやハードリアルタイム制御ループに収まるという主張ではありません。

### 紙を超えたプレゼンテーション

バンド型のページ分割——レポートヘッダー、ページヘッダー、グループ化、詳細、フッター——は、紙への印刷のために発明されました。`.mad` のレイアウトはパラメトリックなデータであり、行キャッシュはローカル SQLite であるため、紙のページはデータの定義ではなく、データの一つのプレゼンテーションにすぎません。

定義とそのマテリアライズされたテーブルを分離しておくことで、同じデータオブジェクト上で他のプレゼンテーションが可能になります。インタラクティブなテーブルとデータエクスプローラー、ネイティブアプリケーションのビュー、チャートとダッシュボード、アプリケーションに組み込まれたビュー、およびブラウザベースのビューアです。従来のページ分割レポートは引き続き重要です。目的は、それらをいくつかある有用なプレゼンテーションの一つにすることであり、廃止することではありません。

### AI が作成するドキュメント

MAD の宣言的な構造は、AI 支援レポートの異なるモデルに適しています。チャートの画像を生成するのではなく、モデルが実際の MAD ドキュメントを提案できます。利用可能なソースとスキーマメタデータを発見し、関連するテーブルとフィールドを選択し、クエリグラフとリレーションシップを構築し、レイアウトを提案し、その結果を検証と実行のためにエンジンに送信します。

責任の分担は重要です。モデルは意図を解釈して構造化された定義を提案し、MAD がそれを検証して実行します。モデルは任意の未検証の SQL ではなく、クエリグラフとレイアウト定義を生成すべきであり、エンジンは SQL の生成、データアクセス、およびマテリアライズに引き続き責任を負うべきです。

その結果は、一度きりの答えではなく、通常の編集可能な `.mad` ドキュメントになります。クエリグラフを検査し、結合とフィルタを編集し、プレゼンテーションをカスタマイズし、モデルなしで結果を更新し、ドキュメントを他の場所で再利用できます。これにより、ユーザーは成果物の制御を保ち、運用が作成した AI に依存することを避けられます。認可、検証、およびデータ保護の制御は、これを実現するための一部となるでしょう。構造的な検証だけでは、分析が意味的に正しいことを証明することはできません。

### オプションのサーバーおよび Web デプロイ

ネイティブアプリケーション、組み込みコンポーネント、およびヘッドレス実行は、引き続き第一級のものとして扱われるべきです。将来のサービスは、スケジューリング、ドキュメントカタログ、アクセス制御、スナップショット管理、共有レポート、および API を追加でき、ブラウザベースのデザイナーはネイティブクライアントと同じドキュメントモデル上で動作できます。

エンジンとドキュメントフォーマットは共通の基盤であり続けます。ローカル実行、プライベートインフラストラクチャ、またはオフライン運用を必要とする顧客は、エンジンの恩恵を受けるためにクラウドデプロイを採用する必要はないはずであり、将来の Web 実装はクエリのセマンティクスを分岐させるべきではありません。

### レガシーレポートの変換

将来のインポーターは、レガシーなレポート形式の定義をオープンな `.mad` ファイルに取り込める可能性があります。これは、長寿命のレポートライブラリを持つ組織のための互換パスであり、方向性の中心でも、上記の方向性の代替でもありません。

## MAD を使う 3 つの方法

これらは別個の製品でも別個のコードベースでもありません。同じアーキテクチャの異なる使われ方であり、データオブジェクトモデルによって結びついています。

### アプリケーションとしての MAD

データを直接扱う人々のための、完全なクエリ、設計、およびレポーティング体験。ネイティブアプリケーション、ドキュメントのポータビリティ、および実用的なレポーティングを備えます。

### 組み込みエンジンとしての MAD

MAD を自身のソフトウェアやデバイスに組み込む開発者向けの、再利用可能なデータアクセス、クエリ、マテリアライズ、およびレポーティングコンポーネント。ドライバアーキテクチャ、ヘッドレス実行、再利用可能な定義、およびローカル処理を重視します。

### AI が作成するデータプラットフォームとしての MAD

人々が必要な情報を説明すると、モデルが検証済みの MAD データオブジェクトとドキュメントを構築するシステム。構造化された生成、機械による検証、および AI から独立して有用であり続ける編集可能な成果物を備えます。これは提案であり、AI による作成はまだ提供されていません。

## なぜこれが重要なのか

この問題は実用的です。多くの組織は、リレーショナルデータベースと専門的な業務アプリケーションを中心に構築された、大規模で長寿命のシステムを運用しています。彼らは、自社データへの信頼できるアクセス、繰り返しのカスタム開発なしに維持できるレポート、優れたユーザー体験を持つネイティブツール、認証情報とデータの処理場所の制御、既存のデータベースインフラストラクチャの継続利用、およびプラットフォームと環境間のポータビリティを求めています。

難しいのは通常、データを信頼できて使える形にすることです。それを提示することは最終ステップです。MAD はデータ取得、リレーショナルモデリング、マテリアライズ、および実行に投資しており、インターフェースはその作業を隠すのではなく、その上に成り立っています。

その価値は前向きなものです。ポータビリティ、ローカルな制御、コンポーザビリティ、信頼性の高い処理、拡張性、および親しみやすい体験です。企業は、不必要なプラットフォーム依存を受け入れることなく、自社データから有用な答えを得られるべきです。

## 指針となる原則
