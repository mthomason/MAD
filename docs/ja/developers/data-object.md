# データオブジェクト — レポートの定義、そのスキーマ、およびその結果セット

このページではデータオブジェクトを定義します。レポートの定義、そのスキーマ、およびその結果セットを1つの契約として扱うものです。これはマルチソース作業がその上に構築される設計であり、フォーマット仕様は今日出荷されているドキュメントを記述します。

**スコープ:** 2026-10-16に提起された概念——データオブジェクトとは何か、このコードベースでどのように表現されているか、それを形式化するのに何が必要か。同じ会話で述べられたマルチソース／サブレポートの組み立ては、契約の帰結としてここに書き留められており、意図的に構築されていません。
**日付:** 2026-10-16、`445794e11`で読了。
**ステータス:** 設計ドキュメント。提案するもので、何も実装せず、ここにあるものは何も予定されていません。[プロジェクトのビジョン](../vision.html) §1——「レポートとはデータソースからテーブルへの関数である」——が、このファイルが具体化し、コードに名前を付けるビジョンです。

## 1. アイデア、そしてそれがそうでないもの

今日、ユーザーは1つのデータベース（MySQL、SQL Server、またはSqlite3）に対してアドホッククエリを設計し、それがデータのテーブルを返し、レポートはそのデータの上にレイアウトツールで構築されます。レポートはクエリとレイアウトです。一般化とは、クエリの半分を取り出してそれをオブジェクトにすることです。

> データオブジェクトとは、**スキーマ**と**結果セット**を生成する名前付き定義です——レポートのクエリを、そのレイアウトから分離し、アイデンティティを与えたもの。その出力はリフレッシュされ、アドレス指定され、別のデータオブジェクトのソースとして使えます。レポートとは、データオブジェクトと、そのオブジェクトの列にバインドされたプレゼンテーションです。

ユーザー自身の言葉（2026-10-16）: *「一種のスキーマと結果セットを返すもので、レポートはアドホッククエリ、レポーティング、デザインである。」*

3つの帰結があり、それぞれ以下で追跡します。

1. **クエリが製品の境界になる。** 同じオブジェクトが、デザイナ（MAD Queryタブが編集するもの）、ビューア（リフレッシュが実行するもの）、CLI（`mad refresh`が実行するもの）、将来のウェブサーバー（エンドポイントが実行するもの）、そしてAI（下書きし、エンジンが検証するもの）に使われます。1つの定義、多数の消費者——これはオブジェクトが独自の名前とスキーマを持って初めて真になります。
2. **オブジェクトは合成する。** *「アイデアは複数のものをリンクすることだろう。レポーティングの世界では、これはサブレポートになる」*（ユーザー）。データ用語では、派生テーブルのDAGです。あるオブジェクトの出力は別のオブジェクトへのテーブルであり、今日のスキーマテーブルとまったく同じです。
3. **ソースは機能ではなく帰結として増える。** ソースデータベースごとに1つのオブジェクト——それぞれがすでに独自のドライバと接続を持つ——をマテリアライズし、その出力で結合します。ユーザーのスケッチ: *「MySQLをサブレポートでクエリし、SQL Serverをサブレポートでクエリし……そしてそれらのレポートを、クエリデザイナで出力によってテーブルとしてリンクできる。」* [プロジェクトのビジョン](../vision.html) §1も同じことを言っています。フェデレーションエンジンは不要で、スナップショットが*フェデレーションそのもの*です。

明示的に**そうでない**もの:

- フェデレーションエンジンではない。MySQLとSQL Serverに1つのステートメントで話す新しいものはありません。各オブジェクトは自身のソースに対して実行され、結合はすでにローカルな結果の上で行われます。
- 2つ目のクエリ実装ではない。SQLジェネレータ、ドライバ、結果テーブル、SQLite結合エンジンはすべて存在し、§5はそれらの上に載る組み立てです。
- 2パスの全件取得キャッシュパラダイムの変更ではない。キャッシュは負荷を支えており、意図的に大きい（`MAD_FORMAT.md` §5.1）。データオブジェクトは、キャッシュが今日すでに保持しているものを正確に生成します。

## 2. 語彙。「スキーマ」はこのコードベースで4つの異なるものを意味する

| 用語 | それが何か | 今日のクラス |
|---|---|---|
| **ソーススキーマ** | ユーザーがクエリできるデータベースのテーブルとフィールド | ライブブラウジング: `MADDatabaseTable` / `MADDatabaseField`（`MADAPI`）。スナップショット: `RptqDatabaseSchemaTable` / `RptqDatabaseSchemaField`、ドキュメント作成時に一度インポート |
| **定義** | クエリグラフ: どのテーブル、どのフィールド、結合、フィルタ、グループ化、ソート | `RptqQuery` + `RptqQueryTable` / `RptqQueryField` / `RptqQueryLinks` / `RptqQueryPredicate` / `RptqQueryGroup` |
| **結果スキーマ** | 出力の列: 名前、型、ネイティブ型、長さ／精度、主キー、非NULL | `MADDataColumn`（列ごとに1つ）、テーブル上に保持 |
| **結果セット** | 行 | `MADDataTable`クラスクラスタ。`MADDataTableFast`としてマテリアライズ |
| **マテリアライゼーション** | ディスク上の結果セット: SQLiteテーブルとそのシリアライズされたスキーマ | `<tag>.maddb`（SQLite）+ `<tag>.mdcache`（plist、`MADDataTable -copyPlist`）、ドキュメントのキャッシュディレクトリ内 |
| **スナップショット** | `MAD_FUTURE.md`の言葉: 名前、バージョン、アドレスを与えられたマテリアライゼーション | 存在しない。§4.3がその始め方 |
| **ストアスキーマ** | 上記すべてとは無関係: ドキュメント自身のストレージフォーマット | `MADStoreSchema`（`MAD/Source/rptq/store/`） |

今日のドキュメントは定義とレイアウトを保持し、マテリアライゼーションはその隣に、ドキュメント（定義ではない）をキーとして存在します。この分割は正しいものであり（`MAD_FORMAT.md` §5）、この設計はそれを保ちます。

## 3. アイデアが今日どのように表現されているか

データオブジェクトの各部分はすでに存在し、異なるレイヤーに、異なる目的のために構築されています。以下はそれぞれの正確な状態と、形式化がつまむことになるシームです。

### 3.1 定義は存在する — `RptqQuery`とそのグラフ

クエリグラフはコンパイルするのに十分完全です。テーブル（`RptqQueryTable`、`alias`と、1つのスキーマテーブルを複数回含められる`dropIndex`付き）、射影（`RptqQueryField`——スキーマテーブル+スキーマフィールドID）、結合（`RptqQueryLinks`、リンク型付き）、フィルタ（`RptqQueryPredicate`）、グループ化（`RptqQueryGroup`、`RptqQuery -sortDescriptorsForDatabase:`経由でソート記述子を駆動）、そして痕跡的なソート行（`RptqQuerySort`、デバッグ記述だけが読む）があります。デザイナは`MADModel*`読み取りモデルを通じてそれを編集します（「`Rptq`を通じて書き、`MADModel`を通じて読み観察する」——`MADModel_Layer.md`）。

グループ化はクエリレベルの定義であり、レポートセクションではありません。`RptqQueryGroup.hasField`はクエリがグループ化するフィールドを、`sort`はその方向を名指しします。クエリが実行されるには、各グループのフィールドがドキュメントが選択するクエリテーブルに属さなければなりません（`hasField.inQueryTable`）。グループ化は結果行上の順序付きキーとしてマテリアライズされ（`-sortDescriptorsForDatabase:`）、フォーマッタはそのキーを比較してグループ境界を見つけます。レポートのグループヘッダー／フッターセクションはそのグループのプレゼンテーションにすぎません——グループ化フィールドを表示する要素を1つも含まなくても、グループ化は依然として行われます。レイアウトが欠けているグループ化フィールドを補うことはできないため、フィールドがnilのグループ、または選択されたクエリテーブルに裏付けられていないフィールドを持つグループは無効なドキュメントです。デザイナは壊れたグループが見えるようにそのようなセクションを構築しラベル付けしますが、クエリ実行とレンダリングは`NSInvalidArgumentException`でそれを拒否し、グループをログに記録します。

そのアイデンティティに関する2つの事実:

- `RptqQuery`は`RptqDatabase`行にぶら下がり、「それぞれの最初のもの」を通じてドキュメントに到達します。`RptqDatabase -defaultQuery`は`hasQueries.anyObject`（`RptqDatabase+Extras.m:88`）、`RptqDocument -mainQuery`も同様です（`RptqDocument+Extras.m:184`）。
- ストアはすでに多数を許容しています。`MADModelDocument`は**`RptqQuery`行ごとに1つの`MADModelDatabase`**を構築し（`MADModelDocument.m:210-240`）、コード自身のコメントは「現在のバージョンのソフトウェアは1つのデータベースとクエリだけを使う」と述べています。基数はアプリのフローの慣習であり、ストアのものではありません。

### 3.2 コンパイラは存在する — `MADQueryFull`

`MADQueryFull -copySQLWithManagedObjectContext:error:`（`MADQueryFull.m:133`）がSQLを構築します。射影される列は`MADQuerySelectExpressionActiveFields`から来ており、これはレポートの*要素*、リンク、グループが参照するすべてのフィールドを`MADQueryActiveQueryFields`に尋ねます。FROM/JOINはテーブルとリンクの`MTGraph`からトポロジカルソートされてコンパイルされ（`:170-204`）、述語とリテラルの引用は`MADDatabase`（`newSafeIdentifier:`、`newSafeLiteral:`）を通り、`LIMIT`は`sqlLimitClause:`経由です。

これは`MAD_FUTURE.md` §3が差別化要因として数える決定論的で所有されたSQL生成です——それは存在し、ヘッドレスです（Linuxビルドでは`MADSources.cmake:93`）。

**しかしそれはドキュメントに溶接されています。** `MADQueryFull`は初期化されたクエリを`queryObject`（`:79`）に保存し、**決してそれを使いません**。SQLパスはドキュメントの最初のデータベースと最初のクエリを再読します（`:147-149`）。また`-getSql:error:`を実装していない（ベースは`@""`を返す、`MADQuery.m:48`）ため、汎用の`MADDatabase -executeQuery:withError:`パスはドキュメントのメインクエリをまったく実行できません。渡したクエリオブジェクトは何が実行されるかを決めません。

### 3.3 実行シームは存在する — `MADDatabase`

抽象点は`-[MADDatabase executeSQL:fieldKeys:onConnection:intoResultTable:withError:]`（`MADAPI/Source/MADDatabase.m:147`、3つのドライバすべてが上書き）です。その宛先は`id <MADDataTableWriting>`と型付けされています——*任意の*書き込み可能なテーブルであり、特定のテーブルクラスではありません。充填契約はドライバ間で均一です。`removeAllObjects` → `addColumn:` → `beginBulkInsert` → `addRowWithDataForFieldKeys:` → `endBulkInsert`（`MAD_DATA_OBJECT`のドライバ: MySQL `MADMySQLFetch+DataTable.m:148-235`、SQL Server `MADDatabaseSQLServer.m:485-571`、Sqlite3 `MADDatabaseSqlite3.m:474-540`）。

ドライバはまた、クエリが`MADQueryDataTableProtocol`に準拠している場合、ドキュメントのターゲットテーブルよりクエリ自身のターゲットテーブルをすでに優先します（`MADQuery.h:28-50`。各ドライバの`-executeQuery:`がそれを確認します——例: `MADDatabaseMySQL.m:331-339`）。プロセスごとに複数の結果テーブルを持つことは意図された拡張ポイントであり、サンプルデータクエリファミリだけが行使しています。

ドキュメントレベルの縫合は`MADOperationRefresh`（`MADDesigner/Source/MADOperationRefresh.m`、131行、UIKitゼロ）です。認証情報を受け取り、`document.mainQuery` → SQL、`document.database`が接続し、`document.dataTable`に実行し、`dataTableMakeCache`が`.mdcache`を書き、`document.refreshed = YES`とします。それはCLIのrefresh動詞でもあり、`CLI/build.sh`の`REFRESH_SOURCES`によってターゲット境界を越えてコンパイルされます（`ROADMAP.md` §3.4）。それは*実行*ではなく*リフレッシュ+永続化+公開*です。共有ドキュメント状態にハードワイヤードされ、`self.dependencies`を検査して認証情報を発見し、ドキュメントを変更します。

### 3.4 戻り値は存在する — `MADDataTable`と`MADDataColumn`

`MADDataTable`（`MADFoundation/Source/MADDataTable.h`）は、その仕事全体が「スキーマと行」であるクラスクラスタです。ベースにメタデータと永続化、サブクラスごとにストレージ（メモリ内の`MADDataTableVirtual`、SQLite上の`MADDataTableFast`）を持ちます。スキーマオブジェクトは`MADDataColumn`です——`identifier`、`fieldName`、`caption`、`type`（`MADDataType`）、`nativeType`、`dataLength`、`dataPercision`、`isPrimaryKey`、`isNotNull`、`isAutoIncrement`、`defaultValue`——第一級でシリアライズ可能な列記述です。

そしてスキーマはすでにディスク上の行から分離可能です。`-copyPlist`（`MADDataTable.m:238-253`）は名前+列キー+列plist+行カウンタをシリアライズし、**明示的に行を含めません**——それがまさに`.mdcache`ファイルであり、`MADDataTableFast`が書き読みします（`-copyPlist` / `-loadWithPlist:`。`MAD_FORMAT.md` §5.3）。

このレイヤーで欠けているもの:

- **スキーマ専用APIがない。** クエリの結果スキーマを実行せずに返すものはありません。スキーマとデータは1つのオブジェクトで、決して2つではありません。スキーマは*行から*発見されます。
- **ゼロ行のSqlite3結果はスキーマを完全に失う。** Sqlite3ドライバは最初の`SQLITE_ROW`反復の内側でのみ列を発見するため（`MADDatabaseSqlite3.m:496-535`）、空の結果は列もDDLもないテーブルを生成します。MySQLとSQL Serverは行が到着する前に結果メタデータから列を追加するため、このギャップはSqlite3固有です。
- `MADDataTableFast`の`columnKeys`は生成された`c<hash>`名であり、フィールド名ではありません。使用可能なスキーマ表面は`MADDataColumn`の`columns`辞書です。そして`for (x in fastTable)`は静かに何も生み出しません——ベースは0アイテムを返し、Fastは`countByEnumeratingWithState:`を上書きしません。呼び出し元は`objectEnumerator`を使わなければなりません。

### 3.5 マテリアライゼーションは今日SQLiteテーブルである

`MADDataTableFast`はテーブル上の抽象ではなく、*テーブルそのもの*です。各インスタンスは`<tag>.maddb`内の1つの物理SQLiteテーブル`t<tag>`を所有し（`-tableName` `MADDataTableFast.m:498`、`-filenameCacheMadDB` `:399`）、列は`c<hash-of-fieldName>`です。2つ目の接続（`databaseForSelects`）が選択側を実行します。グループ化はその1つのテーブル上のインデックスであり（`-sortUsingDescriptors:` `:737`、`-setupGroupKeyIndexes` `:545`、グループプレフィックスレベルの数だけインデックス）、集計はキャッシュ上のSQLです（`MADQueryCacheAggregateFunction`、`MADocument -dataForRows:column:groups:function:groupBy:`が駆動）。**ソースデータベースには`GROUP BY`が一切生成されません**——検証済み: その文字列はどのソースファイルにも現れません。ソースはフラットにクエリされ、グループ化または集計されたものはすべて、マテリアライゼーション上でSqlite3によってローカルに計算されます。

2つの示唆的なスタブが、アーキテクチャが*多数*のテーブルを求める理由を示しています。クラスファクトリ`MADDataTable+Constructor`（`newDataTableOfType:withObjectID:cacheDirectory:`——物理はIDをタグとして`MADDataTableFast`にマップ、`:56-78`）は、2つ目、3つ目のテーブルを構築上安価にします。そして`-cacheTableNameForGroupLevel:`（`MADDataTableFast.m:813`）はグループレベルごとにテーブル`s<level>`を名付けるはずですが、**呼び出し元がありません**。それが示唆するグループ化ごとのテーブルは決してマテリアライズされません。

**アドレスはファイル名です。** ドキュメントのテーブルは`initWithId: fileURL.lastPathComponent.hash`（`MADocument.m:269-283`）で作成され、キャッシュディレクトリは`dataTableIdHash`と名付けられます（`MADURLFactory newURLCacheFilesDirectoryForFilename:`）。ドキュメントごとに1つの結果テーブルがあり、その名前はドキュメントが名前変更されると変わり、何もそれを指すことができません。

### 3.6 欠けているもの、1つの表で

| レイヤー | 存在する | データオブジェクトに欠けているもの |
|---|---|---|
| 定義 | 完全なクエリグラフ。読み取りモデル。ストアは多数のクエリを許容 | 独自の名前とアイデンティティ。別のデータオブジェクトになり得るソース参照 |
| コンパイラ | グラフからの決定論的SQL | 「ドキュメントの最初のクエリ」からの自由。スキーマ専用パス |
| 実行 | 任意の`MADDataTableWriting`ターゲット。3つのドライバ。クエリごとのターゲットテーブル | リフレッシュではない実行——ドキュメントの変更なし、認証情報は発見ではなく渡される |
| 結果値 | `MADDataTable` + `MADDataColumn`。スキーマ専用永続化（`-copyPlist`） | 実行なしのスキーマAPI。ゼロ行のスキーマ喪失 |
| マテリアライゼーション | 実際のSQLiteテーブル`t<tag>`。ローカルのグループ化と集計 | タグ=ファイル名ハッシュ。慣習によりドキュメントごとに1テーブル |
| バインディング | レイアウト → `referencesQueryField` → レンダー時に`MADDocumentObjectDataReference*`で解決 | *ドキュメントの*単一クエリではなく*ある*データオブジェクトへのバインディング |
| アドレス | — | すべて |

3つのハードワイヤリングポイントが具体的なブロッカーであり、3つともコードに見えます。

1. `MADQueryFull`は自身のクエリオブジェクトを無視します（`MADQueryFull.m:147-149`）。
2. `MADDocument -dataTableForQuery:`は`MADQueryFull`に対して`self.dataTable`を返し、それ以外にはnilを返します（`MADocument.m:908`）——1スロットのスイッチです。
3. `MADQueryActiveQueryFields`はクエリスコープなしでストア内の**すべて**の要素、リンク、グループをスキャンします（`MADQueryActiveQueryFields.m:27-99`）。自身のヘッダーのFIXMEはこう述べています。*「現在、ソフトウェアは1つのクエリオブジェクトしか扱わない。」* 2つ目のクエリのフィールドは最初のクエリのSELECTリストに漏れます。

## 4. 契約

### 4.1 コードでの形（提案、例示）

2つの半分を意図的に分離します。

```objc
@protocol MADDataObjectSchema <NSObject>            // describe: no database needed
- (NSArray<MADDataColumn *> *)resultSchema;          // columns, types, from graph + snapshot
@end

@protocol MADDataObjectExecuting <NSObject>          // execute: yields the materialization
- (nullable MADDataTable *)executeIntoDataTable:(nullable MADDataTable *)target
                                      credentials:(MADCredentials *)credentials
                                            error:(NSError **)error;
@end
```


名前は例示であり、分割が要点です。**Describe**は接続、認証情報、行なしで動作しなければなりません——グラフと保存されたスキーマスナップショットから——なぜならそれがデザイナが描くもの、AIが検証する対象、ウェブサーバーが一覧するもの、名前変更されたドキュメントが壊せないものだからです。**Execute**はターゲットテーブルと認証情報を引数に取り、テーブルを返さなければなりません——ドキュメントの変更なし。そうすれば`MADOperationRefresh`は「executeを呼び、永続化し、公開する」に縮み、CLI、サーバー、テストがすべて同じものを呼びます。

### 4.2 実行せずにスキーマ

これは契約が本物である最初の正直な証明です。なぜならそれは*導出可能*であり、今日何もそれを導出しないからです。結果スキーマは`MADQueryFull`がすでに計算するSELECTリストそのもの——アクティブなクエリフィールド、`Table.Field`でエイリアスされ、集計とグループ化が射影するものを加えたもの——です。型と幅はスキーマスナップショット（`RptqDatabaseSchemaField`）から、集計列は`MADAggregateFunctionType`から来ます。作業はSELECTリストの構築を実行から分割し、それを`MADDataColumn`として返すことです。また、行の前に列が存在する瞬間に、ゼロ行のSqlite3ギャップも無料で修正します。ドライバはすでに`addRow:`の前に`addColumn:`を行い、テーブルのDDLは最初の列で作成されます（`MADDataTableFast.m:526-543`）。

### 4.3 アイデンティティとアドレス

データオブジェクトには、名前変更を生き延びる名前と、再生成を生き延びるアドレスが必要です。

- **アイデンティティ:** 他のすべての`Rptq`エンティティと同様、ストア行の`identifier`、および人間向けの名前。マテリアライゼーションのタグはオブジェクトの識別子ハッシュになり、`fileURL.lastPathComponent.hash`ではありません——これはこの目的のために、ファイル名をキーとするアドレッシングを退役させます（`MAD_FORMAT.md` §5.3の危険。`MAD_FUTURE.md` §2.2の「コンテンツハッシュをキーに」という注記はレンダーレイヤーの同じ修正です）。
- **アドレス:** キャッシュディレクトリはすでにドキュメントごとに1つの`.maddb`を保持しています。自然な形式化は、その中に**データオブジェクトごとに1つの`t<tag>`テーブル**を置くこと（タグはすでにそれらを区別します）、それぞれが独自の`.mdcache`形式のスキーマplistを持つことです。オブジェクトごとの`.maddb`ファイル（`t<tag>`/`<tag>.maddb`の対を文字通りに取る）が代替案であり、§5.1がいつ重要になるかを述べています。

### 4.4 ストアが変わるところ — そしてすでに許容していること

最小の形、推奨:

- `RptqQuery`が名前を得る（すでに定義であり、何も移動しません）。
- `RptqQueryTable`の参照——今日は1つの`RptqDatabase`内のスキーマテーブルID——が2つ目の種類を得ます。**別のデータオブジェクト**です。これは合成が必要とする唯一のスキーマ変更であり、追加的です。スキーマテーブル参照を持つv1行は、今日と同じ意味です。
- マルチソースはストア変更をまったく必要としません。ストアはすでに多数の`RptqDatabase`行をサポートし、それぞれが独自のクエリを持ちます（`RptqQuery`ごとに1つの`MADModelDatabase`、§3.1）。今日のドキュメントがそれぞれ1つずつ持つのは、作成フローが1つ作るからです。スキーマは2017年に将来対応され、今も待っています。

より重い代替案——定義を所有する新しい`RptqDataObject`エンティティを作り、`RptqQuery`を降格する——は、よりクリーンな命名とより大きな移行です。決定9.1として記録されています。

## 5. 合成 — サブレポートの組み立て、文書化され、構築されていない

**このセクションは意図的に予定されていません**（ユーザー、2026-10-16: *「組み立てたくはない……しかしこのアイデアを文書化したい」*）。それが存在するのは、必要になったときに発見ではなく計画であるためです。

### 5.1 メカニズム、正確に

1. 各データオブジェクトは自身のソース——自身の`RptqDatabase`、ドライバ、認証情報——に対して実行され、自身のSQLiteテーブルにマテリアライズします（§4.3により、ドキュメントのキャッシュ内の`t<tag>`）。
2. 合成するオブジェクトのクエリグラフは種類として変わりません。その「テーブル」にはデータオブジェクトが含まれ、結合、フィルタ、エイリアスはすべて適用されます。両側でテーブルとは名前付き列の集合だからです。
3. 実行はオブジェクトDAG上でトポロジカルです（`MADQueryFull`が結合グラフですでに実行するのと同じアルゴリズム、`MADQueryFull.m:202`）。ソースが先、合成するオブジェクトが最後、その結果は他のものと同様にマテリアライズされます。
4. 合成するオブジェクトは**リモートデータベースではなくキャッシュに対して**実行されます——その「データベース」が`.maddb`であるクエリです。`MADSqlite3`はすでに完全な`MADDatabase`であるため、このステップのドライバは今日出荷されています。複数の`t<tag>`テーブルを保持する1つの`.maddb`は`ATTACH`をまったく必要としません。`ATTACH DATABASE`は**別々のファイル**——オブジェクトごとに1つの`.maddb`、または*異なるドキュメント*のオブジェクト——の変種であり、サブレポート境界がファイル境界である場合に`ATTACH`（またはコピーイン）が唯一の結合経路です。

一行版は、これがプロジェクトではなく組み立てである理由のすべてです。**すべてのクエリの結果はすでにSQLiteテーブルであり、SQLiteはすでにドライバです。** フェデレーションエンジンは箱の中にあり、現在はファイル名ハッシュでアドレス指定されています。

### 5.2 求められた場合に構築されるもの

1. §4の契約（describe/execute、アイデンティティ、アドレス）——前提条件であり、フェーズではありません。
2. ソース種別: `RptqQueryTable` → データオブジェクト。SQL生成はそれを`db.table`ではなくオブジェクトのマテリアライゼーションテーブルに解決します。
3. 実行順序: DAGを歩き、古いオブジェクトをリフレッシュし、次に合成クエリを実行します。
4. デザイナのテレスコーピング（ユーザーの言葉）: Add Tableパネルで、スキーマテーブルの隣に2つ目の種類のソース——ドキュメントの他のデータオブジェクト、または他のオブジェクトの出力フィールドを一覧するサブレポートボックス。結合UIは変わりません。両端はフィールドです。
5. クロスファイル合成が求められた場合の`MADDatabaseSqlite3`の`ATTACH`サポート。

### 5.3 なぜ一行ではないか

見積もりを正直に保つために記録します。§3.6の3つのハードワイヤリングポイント（`MADQueryFull`の再読、1スロットの`dataTableForQuery:`、スコープされていない`MADQueryActiveQueryFields`）はそれぞれ、2つ目のクエリ——まして*ネストされた*クエリ——が実行できる前に倒れなければなりません。`MADModelDocument`は変更パスで`firstQuery`だけをミラーし（`MADModel_Layer.md` §8）、`RptqQuery -sortDescriptorsForDatabase:`はドキュメントの単一キャッシュに対してグループ化します。どれも難しくはありませんが、すべてが現在の単一クエリアプリにとって負荷を支えています。

## 6. CLI、ウェブサーバー、およびエンジン

ユーザーの問い、2026-10-16: *「CLIは本当にテスト、理解、将来の使用のためのもので……重要だが、目標はウェブサーバーから呼び出せるものを持つことで、CLIがその最良の方法かどうかはわからない。」*

成果物が現状のままでの正直な答え:

- **CLIはエンジンのクライアントであり、エンジンではない。** その6つの動詞——`inspect`、`schema`、`query`、`refresh`、`export`、`write`——は、§3の呼び出しチェーンのサンプル呼び出しサイトです。コンテナを開き、ストアを読み、SQLを生成し、テーブルに実行し、レンダリングします。ウェブサーバーが必要とするのは、安定したエントリポイントの背後にある同じチェーンです。サブプロセスはそのチェーンの1つのバインディングであり（`MAD_LINUX.md` §2がスケッチする形: サブプロセスとしての`mad --format json`）、リンクされたライブラリは別、インプロセスのObjective-C/Swift APIは3つ目です。
- **エントリポイントが欠けている部分であり、それは名付けられています。** `.mad`を開き、クエリを実行し、行を返すUIKitフリーのトップレベルクラスは今日存在しません。Appleでは`MADocument`は`UIDocument`であり、CLIの`MADCLIDocument`は*振る舞い*としてはヘッドレスですが、そのUIDocumentのためにランループを待ちます。（Phase Dはヘッドレス側を解決しました。`MADHeadlessDocument`はLinuxのエントリポイントであり、Phase E以降はレンダー半分も担います——`MADDocumentRenderProtocol`、`MADReportPageBuilder`——ので`mad export`はそこで実行されます。`MAD_LINUX.md` §9。）§4の契約は、そのようなエントリポイントが公開するものです。open → データオブジェクトを一覧 → describe → execute → （スキーマ、行）。
- **ワイヤフォーマットは1つの決定であり、3つではない。** スキーマ+行をJSONとして持つことは、JSONエクスポート（`MAD_CLI.md` §8.3、`ROADMAP.md`の決定表）とAIレイヤーが検証する構造化出力（`MAD_FUTURE.md` §7）と同じ形です。`MADDataColumn`はすでにplist可能な列記述であり、`.mdcache` plistはすでにシリアライズされた結果スキーマです。JSONの形を一度、公開の場で設計すれば、エクスポート、API、AIがすべてそれを消費します。
- **CLIが責任を持ち続けるもの**は`ROADMAP.md` Track 3が設定した規律です。アプリを脇に置いてドキュメントを見えるようにすること、エラー語彙としての終了コード（0〜5）、フォーマットを固定するラウンドトリップフィクスチャ。それらはウェブサーバーに移動せず、ウェブサーバーのエンジンを正直に保つ方法です。

「契約が存在すればこれは安い」という背後にある測定済みの事実: データパスはすでにヘッドレスです——SQL生成、ストア、`MADDataTableFast`、3つのドライバすべてが今日Linuxでコンパイルされ、124のテスト実行ファイルと1,270のテストがグリーン（`Linux/README.md`）。Phase D以降、CLIはそのイメージ内でビルド・実行されます（`inspect`、`schema`、`query`、`refresh`、`export`、`write`）。したがって続く順序は、契約が最初、エントリポイントが2番目、フロントエンドが3番目であり、「CLIかウェブサーバーか」をアーキテクチャの分岐ではなく二行の答えを持つ問いにします。

## 7. 何が必要か — 既存のトラック上で、フェーズに分けて

アプリが出荷を続け、スイートが全体を通じてグリーンを保つように順序付けられています。各フェーズは引退させる§3の変更を名指しします。

| フェーズ | 作業 | 引退させるもの |
|---|---|---|
| 1 | **契約。** `MADQueryFull`のSELECTリスト構築を実行から分割し、`MADDataColumn`として返す。describe/executeプロトコルを追加し、`MADOperationRefresh`にそれらを呼ばせる。振る舞いの変更なし。 | スキーマ専用APIの不在。ゼロ行Sqlite3のスキーマ喪失 |
| 2 | **クエリが自身を所有する。** `MADQueryFull`は与えられたクエリを取る（ドキュメント再読なし）。`-dataTableForQuery:`はクエリごとに解決する。`MADQueryActiveQueryFields`はクエリにスコープする。`MADModelDocument`は任意のクエリをミラーする。1つのドキュメント、多数のオブジェクト。 | §3.6の3つのハードワイヤリングポイントすべて |
| 3 | **アイデンティティとアドレス。** ストアでオブジェクトに名前を付ける。マテリアライゼーションをファイル名ではなくオブジェクト識別子でタグ付けする。キャッシュ内にオブジェクトごとに1つの結果テーブル。オブジェクトごとのスキーマplist。 | ファイル名ハッシュのマテリアライゼーション。ドキュメントごとに1テーブル |

Phase 1は設計の本当のペイロードであり、最小です。ストア変更、UI変更、新しいフォーマットは不要で、すでに存在するコードを並べ替えるだけで、現在のスイートとゼロ行クエリのスキーマアサーションで証明できます。Phase 2〜4は、単一クエリの前提を保持するレイヤーに同じアイデアを適用したものです。Phase 5は組み立てであり、文書化され、予定されていません。

## 9. 未解決の決定

1. **ストアの形。** 既存の`RptqQuery`に名前を付けるか（最小、推奨）、`RptqDataObject`を独自のエンティティとして導入するか（よりクリーン、より大きな移行）?

## 10. 一貫する筋

クエリタブはすでに関数を構築し、リフレッシュチェーンはすでにそれをコンパイルして実行し、結果テーブルはすでにSQLiteとしてディスク上にスキーマと結果セットを持ち、2つを結合するドライバはすでに存在しLinuxでコンパイルされます。それらのどれも持っていないのは、名前、アドレス、describe半分です——「レポートのクエリ」をデータオブジェクトに、データオブジェクトを別のデータオブジェクトが使えるテーブルに変える3つのものです。残り——サブレポート、複数のソース、エンジンの上に立つウェブサーバー——はその上の合成であり、何も新しいものを発明する必要がないからこそ正確に合成します。それは既存のパイプラインを、ファイル名ハッシュより良いものでアドレス指定したものです。
