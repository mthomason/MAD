# MAD Layering and Dead-Code Policy

**Status: decision record, agreed 2026-11-28.** This records how the three representations
relate and what to do with code that is neither finished nor called. It is a policy, not a
refactoring plan: nothing here starts work. The dead-code inventory below is queued as
[`TASKS.md` §20](../registers/TASKS.md#20-the-2026-11-28-backlog-review), item 5.

---

## 1. The three representations

The document has three layers. They were not designed together; the history explains each
one's shape, and the shape is why the boundaries matter.

| Layer | What it is | Written by | Read / observed by | SQL compiled by |
|---|---|---|---|---|
| `Rptq*` | The canonical persistence model: the document's definition as store rows | The application, the converter, the import path | The store layer, the renderer, the exporters | — |
| `MADQuery*` | The SQL definition and compiler: query graph, select expressions, predicates, emitted dialect SQL | The query designer writes `Rptq` rows, not `MADQuery*` objects | `MADQueryFull` and the query-side helpers | `MADQueryFull` |
| `MADModel*` | The document-scoped read model the designer UI binds to | Nobody — it is derived from `Rptq` rows on demand | The Query tab, the visualization canvas | — |

### 1.1 `Rptq*` — the canonical persistence model

`Rptq*` is the canonical model. It is what the application writes, saves, converts, and
renders. It began as **autogenerated Core Data** classes; the store migration kept the
generated headers as a fixed, hand-maintained contract while replacing the backing store
with the portable SQLite schema of our own. The generation step is gone; the contract and
its descriptors are maintained by hand now.

**Never add Core Data back.** The migration removed the last Apple dependency from the
format, and `RptqStoreContext` is the only object graph the code should write. Core Data
survives only in the application target's legacy converter, where it reads documents that
were written before the migration.

### 1.2 `MADQuery*` — the SQL definition and compiler

`MADQuery*` is the SQL layer: the query graph the compiler walks, the select expressions,
the predicates, the dialect-specific statement it emits. It reads `Rptq*` rows and produces
SQL; it does not own persistence, and it does not own display state. `MADQueryFull` is the
entry point that turns a document's query into the statement a driver executes.

### 1.3 `MADModel*` — the document-scoped read model

`MADModel*` is the read model the designer UI binds to. It is not the canonical model. A
model object is a store row identifier plus a weak context plus a few copied display
values, resolved lazily by fetching rows. It exists to give the query UI display-shaped
objects — aliases, adjacency, id-to-metadata lookups — without relation traversal, and to
turn store change notifications into query-graph events. Its scope today is the query side
of the designer and nothing else.

The layer's details, its consumers, and its rough edges are in
[`model-layer.md`](../../developers/architecture/model-layer.md).

## 2. The rule

> **Write through `Rptq`, read and observe through `MADModel`, compile SQL through
> `MADQuery`.**

New code should state which layer it belongs to. A class that mixes two layers is a
question, not a shortcut: the duplicate representations in the tree are what cross-layer
copies produced. Do not add another.

The rule does not mean every file must be classified before it is written. It means the
author answers the question once and keeps the answer: persistence to `Rptq`, display state
to `MADModel`, statements to `MADQuery`.

## 3. Why the file count is not the problem

The 92 query-named files are mostly single-purpose builders. The accidental complexity was
the **Core Data tax** — a fourth, generated representation that had to be kept in step with
the hand-written one — not the three layers themselves. The migration removed that fourth
representation; the three that remain are each doing a job.

**Do not propose merging files.** [`model-layer.md`](../../developers/architecture/model-layer.md)
§7A explains why: the classes' files are referenced by the pbxproj, by both CMake source
lists, by the Linux header shim's per-header symlinks, and by every import site. Merging
them for a cosmetic gain is a project-file change with a long tail across every platform.
The cheap clarity win is per-class header comments and this record, not consolidation.

## 4. The dead-code rule

> **Finish it or delete it; never leave it compiled-nowhere.**

An unfinished start has two honest outcomes:

* **If it encodes an intent the project still holds**, write the intent in this record and
  add a test that will fail until it is wired. Then the code may stay — it is a specification
  with a build, not a relic.
* **Otherwise delete it**, in a dedicated, behaviour-free commit. "Behaviour-free" means the
  commit removes the code and nothing else: no rename, no refactor, no opportunistic fix in
  the same diff, so the removal can be reviewed and reverted on its own.

A file in no target, a method no header declares and no code calls, and a class whose
purpose has been superseded are all the same case. The compiler cannot see them, so the
register has to.

## 5. Non-goals

This record does not merge files, move directories, rename classes, change behaviour, or
start any of the inventory items. It states the rule and the routes; the work is queued in
`TASKS.md` §20 and waits for the user to ask for it.
