# 方向：从报表到可组合的数据

更新于 2026-11-22。本页说明 MAD 设计上要发展的方向。它区分今天已经发布的内容与提议中的内容，并链接公开的设计记录而非内部工作笔记：[数据对象设计](developers/data-object.html)、[多源报表](developers/multi-source.html)以及[格式规范](README.html)。

## 今天已有的内容

一个 `.mad` 文档是报表的**定义**：架构快照、查询图（表、连接、谓词、分组）以及带区布局树。刷新时，引擎把查询图编译为 SQL，一次性读取数据行，并把它们物化到伴随的 SQLite 缓存（`.maddb` + `.mdcache`）中。行数据被有意留在文档之外；定义保持在 100 KB 以下。

引擎已经具备更广阔方向所需的各个部件：

* 开放、可移植的文档格式：一个 bzip2 tar 归档，内含可移植的 SQLite 存储，打开它不需要任何 Apple 框架。
* 查询构建器，把结构化定义编译为 SQL，另有一个用于直接输入的语句的 SQL 解析器。
* 四个 SQL 驱动——MySQL、SQL Server、PostgreSQL 和 SQLite——各自以表的形式返回架构和数据行。
* 本地 SQLite 物化（`MADDataTableFast`），使分组、聚合和重复渲染在手机上切实可行。
* 原生 iOS 和 macOS 应用、原生 Windows 应用，以及通过 `mad serve` 和 `mad` CLI 在 Linux 和 Windows 上以无头方式运行的同一引擎。

有一个后果很容易被忽略：**报表是一个从数据源到表的函数。** 每个驱动都以表的形式返回架构和数据行，而报表的输出*就是*表形式的架构和数据行。引擎已经把两者同等对待。

## 它将走向何方

以下方向都是提议。它们建立在上述架构之上，但除非本页明确说明，否则它们今天都尚未发布。

### 可组合的数据对象

在数据库中，你从 `employee` 或 `sales_data` 这样的基表中选择数据。报表把多张表连接在一起，其输出是一张即席的、物化的 SQLite 表。今天没有任何东西能把查询指向另一份报表的输出：结果缓存确实存在，但它的键是文件名哈希，而不是可寻址的身份。

为该输出赋予稳定的身份，就能让一份报表的结果成为其他报表可以从中选择并与之连接的表。建立在报表之上的报表，构成由派生表组成的有向无环图——一个可移植的语义层：设计报表的同时，也在设计可复用的数据源。[数据对象设计](developers/data-object.html)描述了这一模型，以及形式化它需要什么。

### 多源本地物化

每个驱动都把自己的结果集物化为相同的本地 SQLite 表表示。一旦一份文档可以容纳多个查询定义，并把每个输出寻址为一张表，一份报表就可以把 PostgreSQL 表连接到 SQL Server 表，再连接到 MySQL 表——在 SQLite 中本地合并，中间不需要联邦服务器。每个数据源理解自己的数据；MAD 理解由此得到的表。[多源设计](developers/multi-source.html)记录了架构和各个阶段，其中并非全部都已构建。

### 嵌入式与无头使用

MAD 不必局限于名为 MAD 的应用。同一引擎可以嵌入其他开发者的产品：库存系统、财务应用、制造工具，或需要查询、报表、导出和运营摘要而无需从头构建报表子系统的行业专用管理系统。

宿主应用提供数据访问、集成以及自己的用户体验。MAD 提供可复用的查询、物化、报表和导出能力。驱动的接缝被有意做得很宽——数据源需要提供架构和数据行，而不一定是一个常规的 SQL 数据库——因此同一契约可以容纳关系数据库、本地应用数据、结构化文件和设备。其中一些数据源今天已有驱动；其他的则需要新增驱动。

这一方向也超越桌面软件：资源充足的设备或工业系统可以在本地使用引擎，把测量记录和维护记录转化为诊断报表，而无需持续联网。这并不是说完整引擎能装进微型微控制器或硬实时控制回路。

### 超越纸面的呈现

带区分页——报表页眉、页眉、分组、明细、页脚——是为在纸上打印而发明的。`.mad` 布局是参数化数据，并且行缓存是本地 SQLite，因此纸面页面只是数据的一种呈现，而不是它的定义。

把定义与其物化表分开，使得在同一数据对象之上可以实现其他呈现：可交互的表和数据浏览器、原生应用视图、图表与仪表板、应用内嵌视图，以及基于浏览器的查看器。传统的分页报表仍然重要；目标是让它们成为若干有用呈现之一，而不是抛弃它们。

### 由 AI 编写的文档

MAD 的声明式结构使其适合一种不同的 AI 辅助报表模式。模型不必生成一张图表的图片，而是可以提出一份真正的 MAD 文档：发现可用的数据源和架构元数据，选择相关的表和字段，构造查询图和关系，提出布局，并把结果提交给引擎进行校验和执行。

职责的划分很重要。模型解读意图并提出结构化定义；MAD 校验并执行它。模型应生成查询图和布局定义，而不是任意未经检查的 SQL；引擎则应继续负责 SQL 生成、数据访问和物化。

结果将是一份正常、可编辑的 `.mad` 文档，而不是一次性的答案。可以检查查询图，编辑连接和筛选条件，自定义呈现，在不需要模型的情况下刷新结果，并在其他地方复用它。这让用户始终掌控这一产物，也避免让操作依赖于编写它的 AI。授权、校验和数据保护控制将是让这一切成真的一部分；仅靠结构校验并不能证明一项分析在语义上是正确的。

### 可选的服务端与 Web 部署

原生应用、嵌入式组件和无头执行应继续作为一等公民。未来的服务可以增加调度、文档目录、访问控制、快照管理、共享报表和 API，而基于浏览器的设计器可以像原生客户端一样，在相同的文档模型上工作。

引擎和文档格式仍是共同的基础。需要本地执行、私有基础设施或离线运行的客户，不应为了从引擎中获益而必须采用云端部署；未来的 Web 实现也不应分叉查询语义。

### 旧版报表转换

未来的导入器可以把旧版报表格式中的定义带入开放的 `.mad` 文件。对于拥有长期报表库的组织来说，这是一条兼容路径，而不是方向的核心，也不取代上述任何方向。

## 使用 MAD 的三种方式

这些不是独立的产品或独立的代码库。它们是同一架构的不同用法，由数据对象模型连接起来。

### MAD 作为应用

为直接处理自己数据的人提供完整的查询、设计和报表体验，具备原生应用、文档可移植性和实用的报表能力。

### MAD 作为嵌入式引擎

为把 MAD 纳入自己软件或设备的开发者提供可复用的数据访问、查询、物化、报表组件，重点在于驱动架构、无头执行、可复用定义和本地处理。

### MAD 作为由 AI 编写的数据平台

在这个系统中，人们描述自己需要的信息，模型构造经过校验的 MAD 数据对象和文档，重点是结构化生成、机器校验，以及独立于 AI 仍可使用的可编辑产物。

## 为什么这很重要

这是一个实际问题。许多组织运行着围绕关系数据库和专用业务应用构建的、规模可观且长期的系统。它们希望可靠地访问自己的数据，拥有无需反复定制开发即可维护的报表，获得用户体验良好的原生工具，掌控凭据和数据处理的位置，继续使用现有的数据库基础设施，并在平台和环境之间保持可移植性。

难点通常在于把数据变成可靠、可用的形式。呈现是最后一步。MAD 在数据获取、关系建模、物化和执行上投入，界面建立在这些工作之上，而不是把工作掩盖起来。

价值是正向的：可移植性、本地掌控、可组合性、可靠处理、可扩展性，以及平易近人的体验。企业应当能够从自己的数据中得出有用的答案，而不必接受不必要的平台依赖。

## 这不是什么

不是承诺，不是带日期的路线图，也不声称上述提议已经发布。本页记录的是一个方向。每项能力仍需像仓库中其他东西一样经过设计、测试和文档化，其中一些方向在构建过程中可能会改变。

## 指导原则

> **文档定义工作。引擎执行工作。呈现让结果有用。**
