# MAD 的未来——从文档编辑器到数据对象平台

写于 2026-10-04，基于 `c807eeb4d` 时的 `master`。本文有意保持推想性质：它是一份愿景文档，而不是一份要执行的计划。当它涉及真实工作时，会指向已经存在的各项轨道（`MAD_FORMAT.md`、`MAD_STORE_MIGRATION.md`、`MAD_CLI.md`、`ROADMAP.md` §3-5），以便在相关工作启动时把两者对齐。

---

## 1. 重新定位

用户的提示词，概括如下：

> 不要再把 `.mad` 当作供用户查看的报表文档。把它当作一个数据对象。想一想那些隐藏的文件类型。往企业级去想——在那里，这些文件类型甚至可能根本不会暴露出来。报表可以像表一样被链接进其他报表，因此一个查询可以跨越多个数据源。

架构本身已经认同这一点。`.mad` 文件不是 PDF 意义上的文档；它是一个**定义**——架构快照、查询图、布局树——体积不到 80 KB，而报表*显示*的一切都位于伴随文件中，这些文件是派生的、一次性的，并在刷新时重新生成（`MAD_FORMAT.md` §5）。这一划分已经是：

| 层 | 所在位置 | 是什么 |
|---|---|---|
| 规范 | `.mad` 内部 | 声明式：架构快照 + 查询图 + 布局树 |
| 物化 | `<hash>.maddb` + `<hash>.mdcache` | 结果表：行 + 结果架构 |
| 呈现 | `<hash>*.madac` | 预渲染页面，以布局和页面几何为键 |

因此，这一重新定位在架构上不付出任何代价。它改变的是我们*如何称呼*这些东西，以及我们*允许*它们做什么：

- **报表是从数据源到表的函数。** 查询图是函数体；引擎把它编译为 SQL；`.maddb`/`.mdcache` 这一对就是返回值——一张带有架构的表，与任何数据源返回的表无法区分。
- **引擎已经能够把任何表作为数据源。** 每个数据源驱动都以表的形式返回架构和行。报表的输出*就是*表形式的架构和行。唯一缺失的一环是**寻址**：没有任何东西能把查询图指向另一个报表的输出，因为该输出是按文件名哈希作为键的缓存，而不是一等对象。
- **一旦闭环，产品就改变了性质。** 如果报表 R 的输出可以作为报表 R′ 内部的一张表，那么报表就可以组合，整个系统就变成一个**派生表的 DAG**——一个语义层。针对多个数据源的单个查询随之免费获得：从 MySQL 取快照，从 SQL Server 取快照，在 SQLite 中连接，由第三份报表显示。不需要联邦引擎；快照*本身*就是联邦。

那唯一的一处改变——让隐藏缓存成为一个有名字、可版本化、可寻址的对象——正是本文围绕展开的承重理念。其余一切（Web、云、AI、金钱）都是它的结果。

把这一点落到实处的那份设计——数据对象的契约、它今天对应的代码，以及将其形式化需要分阶段做些什么——是 `MAD_DATA_OBJECT.md`（写于 2026-10-16）。本文是愿景，那一份是设计；其 §7 是本节在工程层面的版本。

## 2. 文件类型的真实身份，以及隐藏类型将变成什么

### 2.1 `.mad` 作为数据对象

作为一个数据对象，`.mad` 有四个值得作为卖点的特性：

1. **可移植。** 容器是带魔数头的 bzip2 tar（`MAD_FORMAT.md` §7）；存储正在迁移到我们自己的 SQLite 架构（`MAD_STORE_MIGRATION.md`，Phase C 已于 2026-10-03 落地，Phase D 待完成）。Phase D 落地后，格式中不再残留任何 Apple 依赖。SQLite 能打开的地方就能打开 `.mad`——而 SQLite 无处不在。
2. **小巧。** 随产品提供的示例样本均小于 80 KB。移动一份报表的定义，比移动它的一张截图更便宜。
3. **声明式且可 diff。** 架构、查询图、布局树——全部结构化、全部可版本化、全部可审查。`.mad` 是一段人类可以审计的*程序*。（这正是 AI 将充分利用的特性，§6。）
4. **可自校验。** 引擎负责生成 SQL，因此图在任何查询运行之前就可被检查。损坏的 `.mad` 会像损坏的程序一样失败，并给出精确的错误——CLI 的退出码已经是这一纪律（`MAD_CLI.md` §3）。

一句话概括这一重新定位：**`.mad` 是源代码；伴随文件是它的构建产物；查看器是执行它的运行时。** 而且和源代码一样，这份产物可跨运行时移植——iOS 应用、CLI、服务器、浏览器。

### 2.2 隐藏文件类型作为产品

三类伴随文件有文档记录，但尚未给出正式规范（`MAD_FORMAT.md` §5.3）。在这一重新定位下，每一类都变成一个产品：

- **`.maddb` + `.mdcache` → 快照（Snapshot）。** 这一对*就是*报表的输出：行加上结果表架构，两者都已经以可移植的方式序列化（SQLite 加一个 plist，其架构现已记录在案）。一个有名字、有版本的快照是：
  - **无需凭据或实时访问即可共享**——把查询结果发给同事，而不用把数据库发给他们；
  - **可审计**——“Q3 结账那天 CFO 的报表说的是什么？”会变成一个由快照存储来回答的问题，而不是一场争论；
  - **离线**——打包文档的问题（`MAD_FORMAT.md` §8.3，`MAD_CLI.md` §8.2）得到*是*的回答，但以一件独立的产物形式，而不是 `.mad` 的一个变体：流动的是快照，`.mad` 保持精简；
  - **作为其他报表的输入**——即 §1 中的组合闭环。
- **`.madac` → 预渲染页面。** 一个渲染一次、向众多客户端提供页面的服务器，正是代码库已经认定的缓存用途：“缓存是未来各种视图的平台”（`MAD_FORMAT.md` §5.1）。在 Web 产品中，渲染缓存不再是设备本地的优化，而成为服务模型。（它还继承了一个绝不能带到服务器上的缺陷：键是文档的*文件名*，而不是其内容，因此同名下的编辑会提供过期的页面——§5.3。在任何服务器开始渲染之前，先把键改为内容哈希。）
- **缓存目录 → 物化存储。** 每个 `dataTableIdHash` 一个目录，按应用自身的规则命名。在服务器上，这将变成一个按文档标识 + 内容哈希 + 页面几何寻址的内容寻址存储，而这正是每个静态资源服务器已经具备的形态。

战略要点：**这些文件类型本身就已经构成产品线。** 这个软件可能成为的公司，销售的是三种对象——定义、快照和渲染后的页面——而不是“一个做报表的应用”。

## 3. 这将成为的核心技术

把各个部件拼在一起，重心就是：**一件可移植的语义层产物**——一份声明式规范，其执行是确定性的 SQL 生成加上 SQLite 中的物化结果，并附带参数化呈现。这正是 dbt（模型建立于模型之上）、Looker（explores）和 Cube（语义立方）所占据的空间，而它们各自都有一个空缺：

| | dbt | Looker | Cube | 以 `.mad` 为中心的平台 |
|---|---|---|---|---|
| 数据模型可移植 | 部分（YAML/SQL） | 否（锁定于 Looker） | 部分 | **是**——一个文件，无需服务器 |
| 呈现随模型一起流动 | 否（BI 工具是外挂的） | 部分（锁定） | 否 | **是**——布局是数据，而不是截图 |
| 一个模型的输出可作为另一个的输入 | 是 | 是 | 是 | **是**——前提是快照可寻址 |
| 离线 / 边缘 / 嵌入式 | 否 | 否 | 否 | **是**——SQLite 到处都能运行，今天就已经能在设备上运行 |

有三个差异化点值得明确点名，因为它们已经是事实：

1. **呈现是参数化的，而不是一张图片。** 布局树（区段、元素、样式、几何）位于定义之中并随之流动。同一个 `.mad` 今天在 UIKit 中渲染为页面，通过 CLI 渲染为 PDF，将来在 Web 查看器中渲染为 DOM/SVG——因为布局是任何渲染器都能消费的数据，而不是画布状态。这一点很罕见：大多数 BI 仪表盘只是服务器的一种意见，而不是可移植的对象。
2. **SQL 生成是确定性的，且由我们掌控。** 引擎从图生成 SQL；用户（或 §6 中的 AI）从不编写 SQL。校验发生在图这一层，在任何查询存在之前。正是这一特性使该格式可以安全地暴露给机器。
3. **物化格式已经是可移植的。** SQLite，页大小为 8192 字节，`.mdcache` 架构已记录在案，各种奇怪的细节也已编目（`dataPercision`、`~MTNull~` 哨兵值——`MAD_FORMAT.md` §5.3）。对于更大的快照，DuckDB 是自然的服务器端继任者（它说 SQLite 方言说得足够好，在大规模场景下可以直接替换），但在规模提出要求之前，没有任何因素强迫我们做这一迁移。

一份同时也是表的报表，业界的名字是**语义层**；定义语义层的产物，业界的名字是**模型**。这个代码库正在悄悄构建的，是一种能在手机、笔记本电脑和服务器上运行、并自带呈现的模型格式。目前还没有人售卖这样的组合。

## 4. Web 版本

### 4.1 为什么它比看起来更近

数据通路已经几乎不依赖 UIKit，而且这是*测量出来的*（`MAD_CLI.md` §4）：`MADDataStructures` 0/37 个文件，`MADFileManager` 0/31，`MADSqlite3` 0/65，`MADMySQL` 0/42，`MADTds`/`MADTdsClient` 分别为 0/3 和 0/9；`MAD` 为 28/464，其中 UI 部分可以按名字识别出来。CLI 已经无头地跑通了整条通路——`inspect`、`query`、`refresh`、`export` 针对两个示例样本都一次成功（`ROADMAP.md` §3.1）。刷新编排（`MADOperationRefresh.m`，131 行，零 UIKit 符号）就是 CLI 的 refresh 动词；它只是位于 App 目标里而已（`ROADMAP.md` §3.4）。

换句话说：**Web 版本的引擎已经存在，而且已经能在没有 UI 的情况下运行。** Web 版本需要的是：(a) 服务器上的引擎，(b) 覆盖 CLI 各动词的 HTTP 层，(c) 一个消费与 App 相同文档树的浏览器 UI。真正的新工作只有 (c)。这一论断针对的是*引擎*，而不是托管：服务器在哪里运行，以及 Web 在引擎周围加上的其他一切，见 §5。

### 4.2 形态

**计划就是做一个克隆。** 按照用户的说法：Web 版本是完整的 iOS 应用，而不是一个削减版的查看器——同样的三标签页体验（MAD Query、MAD Designer、MAD Viewer）和同样的文件浏览器，运行在浏览器中。每个屏幕都能干净地映射：

| iOS 屏幕 | Web 对应物 |
|---|---|
| 文件浏览器 | 一个云目录，展示相同的文档元数据和创建文档流程 |
| MAD Query | 同样的图构建器——表、连接、筛选器、分组——写入相同的查询结构 |
| MAD Designer | 可缩放的画布：绝对定位的区段带区，可在分组之间拖拽 |
| MAD Viewer | 分页预览加上刷新按钮，由相同的快照存储支撑 |

- **服务器。** 服务器端用 Swift（Vapor 或类似方案），链接与 App 相同的 `MADFoundation` / `MAD` / `MADSqlite3` / 驱动框架——前提是 `MAD_CLI.md` §4.2 中的无头子集成为一个真正的打包边界（Swift Package Manager 是自然的载体）。不移植 SQL 生成，不重新实现 `MADDataTableFast`，格式不存在第二个事实来源。CLI 的退出码变成 HTTP 状态码；它的动词变成端点：`inspect` → 元数据，`query` → SQL 预览，`refresh` → 作业队列，`export` → 渲染服务。
- **客户端。** iOS 设计器是一个可缩放的滚动视图，承载嵌套的集合视图，元素可在分组之间拖拽；它在 Web 上的克隆是一个画布应用——Figma 式的，而不是表单式的：绝对定位的带区（报表页眉、页眉、分组、明细、页脚），滚轮/双指缩放，区段之间的 HTML5 拖放。查看器标签页是一个分页预览，把相同的布局树渲染为 DOM/SVG，PDF 来自服务器的导出端点。文件浏览器是一个云目录，显示与 iOS 版相同的元数据。
- **契约是文档树。** 两个 UI 都是同一个存储架构的消费者（`MADStoreSchema` 已经在驱动转换器的属性/边列表——`MAD_STORE_MIGRATION.md` §7 Phase B）。浏览器永远不需要引擎的内部细节；它需要文档树和快照架构，而这两者都已经可序列化。

一个有用的心智模型：**iOS 应用和 Web 应用是同一个引擎的两个完整客户端**——一件产物，多个运行时，而其中两个运行时本身就是完整的产品，就像 JAR 或 PDF 与其查看器之间的关系。iOS 客户端保留了离线和触控；浏览器客户端换来的是触达范围。

### 4.3 分期（草拟，启动时与 `ROADMAP.md` 对齐）

1. **三道接缝**——驱动注册表（`ROADMAP.md` §5.1）、导出协议（`ROADMAP.md` §5.2，text/JSON/CSV 作为新类，而不是新的 switch 分支）、元素协议（`ROADMAP.md` §5.3）。这些是以下一切的前提，而注册表正是解除 `MADOperationRefresh` 迁移和任何 macOS 构建阻塞的关键。
2. **无头打包**——按 `MAD_CLI.md` §4.2，把 `MADFoundation`/`MAD`/`MADSqlite3`/各驱动作为不依赖 UIKit 编译的包，并扩展到 Linux。`MADFoundation` 中四个触及 UIKit 的文件已经被点名并完成分类评估。
3. **`mad` 作为服务**——在现有动词之上的 HTTP API；用于刷新的作业队列；缓存目录变成物化存储（§2.2），`.madac` 的键采用内容哈希。
4. **克隆，逐个标签页**——先做目录，然后 MAD Viewer，然后 MAD Query，最后是 MAD Designer 画布。克隆是目标，而非楔子：与 iOS 应用功能对等，按各标签页相互依赖的顺序构建——查看器证明文档树能在 UIKit 之外渲染，查询标签页证明图编辑可行，设计器则是其上的画布。
5. **组合**——快照作为可寻址的表（§1），然后是调度与血缘（这份报表读的是哪个快照？）。

这一顺序尊重现有文档已经确立的东西：CLI 从来不是一个产品，它是让数据通路变得可见的仪器；Web 服务是同一件仪器穿上 API 的外衣，只有浏览器 UI 是留待以后做出的产品决策。这件仪器会长成什么，见 §4.4；它在哪里运行，以及它周围运行着什么，见 §5。

### 4.4 CLI 的第二幕

今天 CLI 只是用来测试，而且理应如此：它的存在是为了在 App 退到一边的情况下让文档变得可见（`ROADMAP.md` Track 3）。但仪器同时也是胚胎。`mad` 可能变成什么，按其生长的顺序：

1. **可部署的引擎。** 同一个二进制文件就是服务器部署的自然单元：把 `mad` 容器化，在它前面放一个队列和一扇 HTTP 前门，Web 产品的后端*就是*长大后的 CLI。退出码已经是状态码；`--rows N` 已经是分页；动词已经是 API。
2. **报表流水线运行器。** 一旦快照可寻址（§1），报表就构成一个 DAG——而 DAG 需要一个运行器。`mad run` 按依赖顺序刷新一个项目的文档，就像 `dbt run` 构建模型那样：`.mad` 文件放在 git 中，CI 中运行 `mad test`，一份清单（manifest）列出项目的各个文档，坏掉的报表会让构建失败。报表即代码。这是可用的最大一步：从“打开一个文档”到“运营一个目录”。
3. **自动化表面。** 定时刷新并通过电子邮件发送 PDF 的 cron 作业；通过 shell 调用渲染命令的脚本；通过调用一个二进制文件来嵌入报表功能的其他应用。这是穿上命令行的 OEM 故事（§8.8）。
4. **AI 的双手。** 在拒绝并修复循环（§7）中，模型从不直接与数据库对话；它与引擎对话。CLI 是这种对话最字面的形式：对模型的草稿运行 `mad validate`，运行 `mad refresh --dry-run`，退出码就是错误词汇表。一个能运行 `mad` 的智能体已经可以完成真实的报表工作。

这一演进与本文其余部分所描绘的一致：仪器 → 引擎 → 流水线 → 平台。

## 5. 它在哪里运行，以及它周围运行着什么

用户的问题——*“这就是我们要补全 CLI 的原因，对吧？”*——完全正确。CLI 正是让本节可被回答的边界：它是引擎与平台相遇的唯一表面，而每一个平台问题都是关于这一表面另一侧立着什么的问题。

### 5.1 平台矩阵

“这东西必须托管在 Mac 上吗？”不必——但每个候选宿主机都有不同的代价，假装不是这样，正是服务器项目死掉的方式。今天唯一具备服务器形态的运行时是 iOS Simulator：CLI 为它构建，并通过 `simctl spawn` 运行，这也是 `mad export` 能生成 PDF 的唯一原因——它为 `UIPrintPageRenderer` 借用了模拟器的 UIKit。诚实的矩阵如下：

| 宿主机 | 引擎 | 渲染 | 达到该处的代价 |
|---|---|---|---|
| macOS 服务器 | 接近原生——无头子集是测量出来的，不是猜的（`MAD_CLI.md` §4） | CoreGraphics/PDFKit 存在；仍然需要一条非 UIKit 的打印通路 | 无头打包（§9 第 3 阶段），以及先行完成的驱动注册表 |
| Linux 服务器——真正的托管目标 | 核心部分（SQL 生成、`MADDataTableFast`、存储）基于 Foundation 而非 UIKit；Linux 上的 Objective-C 意味着 GNUstep/libobjc2，它能工作，但摩擦是真实存在的 | Apple 的东西一概不存在：pdfium、Skia，或者把页面渲染为 HTML/SVG 让客户端打印 | Compressor 增加 Linux 行——每个内置库都是 Linux 原生的 C，所以这是构建系统的工作，而不是移植；渲染器是一个真正的产品决策 |
| 浏览器——*格式*的第四个运行时 | 没有完整引擎，但 `.mad` 是带文档化存储架构的 bzip2-tar-SQLite；sql.js 在 WASM 中运行 SQLite | DOM/SVG 是原生的 | 一个用于存储架构的 JS 读取器——快照查看可以完全不需要服务器 |
| Windows | 格式文档已经要求在 Windows 上有读取器（`MAD_FORMAT.md` §7）；现实中它是客户端，而不是宿主机 | 与 Linux 相同的非 Apple 渲染器 | 排在最后 |

逐框架审计在 Linux 上编译实际需要什么——测量出的依赖矩阵、垫片（shim）清单、GNUstep 的覆盖风险、工具链，以及带 go/no-go 检查点的分期——见 `MAD_LINUX.md`。它的一句话建议是：把引擎保留在 Objective-C 中，针对 GNUstep 编译，让其他语言跨越 CLI 边界进行集成。macOS 优先的路径避免了做选择；Linux 路径则做不到这一点。正是 CLI 边界让两种答案都可以修订——这也正是为什么要在选择平台*之前*补全它，而不是之后。

### 5.2 Web 增加了 App 从不需要的东西

iOS 应用在设计上就是单用户的：每个设备一个钥匙串，每个设备各自的文档，权限由拿着手机的人来执行。Web 产品从第一天起就是多租户的，而以下这些在代码库中一个都不存在。它们全部位于引擎*周围*，从不进入引擎内部：

- **用户与身份。** 账户、组织、邀请、SSO（OIDC/SAML）。
- **权限与访问控制。** 角色（查看者 / 设计者 / 管理员）、按文档的 ACL、架构级授权——“谁能看到哪张表”从“拿着设备的人”转移到“策略服务器”。
- **许可与计费。** 席位、功能层级、计量（刷新次数、快照存储、导出）。这是 §8.4-8.5 价格背后的机器；iOS 版没有对应物，这是真正的产品工作。
- **凭据保险库。** 按组织存放的服务器端机密，绝不放设备上。悬而未决的钥匙串问题（`ROADMAP.md`，决策表）变成保险库的问题。
- **审计与血缘。** 谁在何时运行了什么；快照版本历史；§2.2 中的合规答案。
- **API 表面。** 密钥、作用域、webhook、用于 OEM 故事（§8.8）的嵌入令牌。
- **内容控制。** 调度、速率限制、快照保留、导出规则。

让这一切变得可驾驭的架构要点是：**上述每一项都挂在 CLI 边界上。** `mad` 保持愚笨——认证、打开、刷新、导出——由平台层来回答*谁可以对哪个文档执行哪个动词*。一次权限拒绝是一个新的退出码；一次计量事件是运行旁边的一条日志。引擎永远不知道“组织”是什么。正是这种分离，使得“补全 CLI”不是 Web 产品的弯路——它是 Web 产品的第一个、也是最难的架构决策，并且在尽可能便宜的地方做出。

## 6. 企业与云

在企业部署中，这些文件类型不再是以 iOS 文件 App 所理解的方式存在的文件：

- **目录取代文件浏览器。** `.mad` 变成一行：名称、所有者、ACL、版本、它所依据的架构快照。文件仍然是*序列化*形式——对象的可移植形态，正如 git blob 是提交的形态——但它不再是用户的交互单元。按引用共享取代了隔空投送式共享。
- **物化存储取代按需刷新。** 用户的“可以按需刷新的隐藏缓存文件”，在服务器端就是整个产品：调度器让快照保持温热；查看器读取快照，从不读取源数据库。这就是云端的护城河——托管版本之所以值钱，是因为它代表数百份文档，在规模化层面拥有刷新、陈旧性和渲染。
- **凭据进保险库，而不是进手机。** `MADKeyChain` 的后代是一个机密管理器；数据库密码归谁所有的悬而未决问题（`ROADMAP.md`，决策表）变成“这个服务使用哪个保险库”。
- **审计从快照中自然产生。** 带版本的快照回答了每家受监管公司最终都会问的合规问题：这份报表在什么日期、向谁、基于什么数据展示了什么。
- **许可证问题已经想了一半。** 交付一个服务器会以新的方式再分发内置库；`THIRD_PARTY_LICENSES.md` / `LICENSE_COMPLIANCE_PLAN.md` 中的 LGPL 义务和 MySQL 换 MariaDB 之事，正是这一问题现成的记录。服务是*友好*的情形（链接，而非传递），但在任何服务器交付之前，必须按部署模型重新审计这些义务。

有两条诚实约束需要点名：(1) PDF 渲染目前是 UIKit 的 `UIPrintPageRenderer`（`MAD_CLI.md` §3）——今天 `mad export` 只有借用模拟器的 UIKit 才能生成 PDF，而真正的渲染器决策在 §5.1；(2) 两遍拉取一切的设计假设报表的规模是给人看的，而不是给数据仓库的——这是一个要*保留*的特性，因为产品的整个立场就是“做报表，不做 PB 级扫描”，但快照大小上限和分页应当从第一天起就纳入服务器设计。

## 7. AI：让模型制作报表需要什么

用户的问题：*要让 GPT 接收用户输入并据此创建报表，需要什么？* 答案很短，因为架构已经是正确的那个：**模型从不编写 SQL，从不绘制像素——它编写图。**

这种分工就是全部的诀窍：

- **引擎负责正确性。** SQL 从经过校验的结构生成，因此糟糕的模型输出会在图校验阶段以精确的错误失败——就像今天损坏的 `.mad` 那样失败——而不是产出一条微妙地错误的查询。不存在 SQL 注入面，因为模型从不接触 SQL 文本。
- **模型负责意图。** “上一季度按地区的销售额，合计放在报表页脚”会变成一个查询图加一棵布局树。两者都已经是结构化数据，而 `MADStoreSchema`——这个已经在为转换器遍历每个实体属性和边的架构驱动——距离成为用于校验 LLM 结构化输出的 JSON Schema 只差一步。
- **接地（grounding）成本很低。** 文档自带架构快照，总共不足 80 KB。模型以该快照为依据——通过工具调用（`list_tables`、`describe_table`），或让快照位于上下文中——从不接触凭据，从不接触实时数据库。引擎居中协调这一切。
- **循环是拒绝并修复。** 模型输出图 JSON → 存储解析器校验 → 精确的错误返回给模型 → 模型修复。CLI 的退出码纪律（`MAD_CLI.md` §3）正是这个循环所需的错误词汇表，而 885 个测试的套件是把校验钉住的测试夹具。
- **Scrimpter 迎来第二次生命。** 一门未被使用的脚本语言在今天是一种死重；在 AI 世界里，报表 DSL 是文档的*文本形式*——是模型输出、人类审查并 diff 的东西。LLM 最擅长输出受约束的语言，而“报表即代码”正是让 AI 编辑变得可审查的原因。这是复活 `Scrimpter` 最强的候选理由，而且值得明说：为人类公式作者构建的编译器，也是 AI 作者所需要的那个。

产品形态：设计器旁边一个聊天窗格——“帮我做一份按所有者和阶段划分的销售管道报表” → 画布上填满图和布局，之后完全可以编辑。后续指令会改变同一张图（“改成按月分组”“加一行总计”）。每个 AI 动作都以普通编辑的形式落地，因此撤销、版本化和 diff 照常工作。聚合由引擎在行缓存上计算——模型从不被要求在数据上做算术，而这正是当前的模型悄悄失败的地方。

成本由快照界定：上下文是架构（很小），而不是数据。一个会复利增长的产品改进：让用户对列做一次注解（“这是预订月份确认的收入”），把注解存进架构快照，之后每一个 AI 会话都继承这套词汇。

## 8. 赚钱的方式

这一重新定位把一个产品变成一个目录。按由近及远的粗略顺序：

1. **App Store，免费增值。** 免费查看器（包括当前损坏的独立查看器目标——它是自然的免费客户端：能打开快照，并在允许时刷新），付费设计器。一次性买断或订阅，但设计器是专业消费者工具，查看器是楔子。
2. **元素与驱动包。** 三道接缝（`ROADMAP.md` §5.1-5.3）变成应用内购买（IAP）目录：图表元素、条码元素（把 `MADBarcodes` 作为付费元素复活），以及——最大的一块——驱动。仅 Postgres 一项就能让可触达市场翻倍；然后是 Snowflake、BigQuery、REST/JSON。每一个都是“继承 `MADDatabase`，返回一个架构”——这也正是项目简介已经做出的可扩展性承诺。
3. **驱动市场。** 第三方 `MADDatabase` 子类，收入分成。可扩展性故事变成一个双边市场；注册表（`ROADMAP.md` §5.1）就是商店的货架。
4. **MAD Server——Web 版本，自托管。** 在浏览器中完整克隆 iOS 体验。按年许可，按席位或按核计费，经典的企业 BI 定价模型（SSRS 时代的公司以及今天的 Looker/Cube/ThoughtSpot 都是这样收费的）。买家是拥有 SQL Server/MySQL 资产、被临时查询请求淹没的公司：MAD 是受治理的自助式 BI——分析师拿到架构和图构建器，IT 保留凭据，语义层保持单一事实来源。
5. **MAD Cloud——托管版本。** 物化存储、调度和渲染是 SaaS 的护城河（§5）。按席位加上刷新/存储计量。快照存储以一种好的方式让流失变得痛苦：报表运行得越久，客户拥有的审计历史就越多。
6. **快照/数据产品层级。** 直接售卖隐藏的文件类型本身：在组织外共享的快照、作为实时报表源嵌入其他工具、血缘与审计。“报表即 API”——导出格式变成内容类型，快照变成订阅资源。
7. **AI 层级。** 自然语言报表构建，溢价提供，定价可覆盖 token 成本。这是为整个语义层正名的追加销售：一个只能构建它能校验的报表的 AI，才是企业真正愿意让它靠近自己数据的 AI。
8. **嵌入式/OEM。** 把引擎和查看器白标给需要在自己产品内嵌报表的 ISV——Telerik/Stimulsoft 模式。CLI 已经具备 SDK 的形态（§4.4），而 `.mad` 作为一个小巧的可移植文件，正是嵌入式合作伙伴想要交付的东西。

有一个战略岔路口应当摆在桌面上：**格式是否开放？** 开放的 `.mad` 规范加上付费运行时（App、服务器、AI），正是造就 dbt、Superset 和 Metabase 的“先开源再售卖”模式——格式成为标准，钱在引擎、托管和市场里赚。封闭格式保护护城河，但给生态设了上限。v1 的魔数头（`MAD_FORMAT.md` §7）两种解读都说得通；这是产品战略决策，应当在规范发布之前做出，而不是之后。

扎根于现有文档已经决定的内容。每一步都保持 App 可交付、测试套件全绿——这正是本项目已经端到端演示过的纪律。

| 阶段 | 工作 | 依据 |

## 10. 这一愿景所隐含的决策

这些都不阻塞今天的轨道；它们是愿景所依赖的岔路，而每一条都有一个自然的答案：

1. **`.mad` 是一个文件还是一个对象？** 两者都是。文件是可移植的序列化；在云中，它是目录里的一行，而这一行的序列化恰好是一个文件。格式文档已经把容器与存储分开，这正是这里所需要的接缝。
2. **打包变体存在吗？** 存在——但作为*快照*产物，而不是 `.mad` 的变体。定义保持精简；数据作为自己的对象流动。
3. **内容变化应当使渲染缓存失效吗？** 应当，而修复就是内容哈希键——很便宜，并且在任何服务器渲染之前都是强制性的。
4. **格式开放吗？** 即 §8 中的战略岔路；在发布规范之前决定。
5. **JSON 导出的形态是什么？** 回答这个问题（`MAD_CLI.md` §8.3）与定义快照的交换格式和 AI 层的结构化输出是同一项工作——一个架构服务三者，因此它应当公开地设计一次，而不是私下设计三次。
6. **服务器首先在哪里运行？** macOS 托管只维护一套代码库，而且今天就有渲染器；Linux 是真正的托管目标，但会打开 Linux 上的 Objective-C 岔路（§5.1）。建议：先在 macOS 上交付，保持 CLI 边界干净，把 Linux 当作一个被追踪的缺口，而不是一次重写。

贯穿这一切的主线：这个代码库不是在构建一个报表编辑器。它是在构建一种可移植、可组合、可被机器检查的方式，把数据源变成派生的数据对象——而这一件事，业界目前正为 dbt、Looker、Cube 和 ThoughtSpot 支付大笔金钱，同时被锁定在它们的云里。那种能装进 80 KB 文件、在手机上运行、按计划刷新、并同时接受来自设计者和语言模型的编辑的版本——那个版本还不存在。这就是机会。
