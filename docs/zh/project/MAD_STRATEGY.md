# MAD Designer——战略分析与前进路径

**由 Claude Code 应用户要求于 2026-10-22 编写；同日扩展了平台相关讨论（驱动即任何能返回表的东西、用户可安装的驱动、把显示表面作为第四道接缝、macOS/Windows 的定位）。** 本文件是一份分析交付物，而非项目文档：它不做任何代码改动，可以自由编辑或删除。它审视仓库状态（`master` 位于 `774a52b70`）以及跟踪与设计文档，并如实回答五个问题：

1. 这个项目价值几何，它是否应该继续？
2. 通往 Web 前端——既定首要目标——的最佳路径是什么？
3. 它如何赚钱：开源、企业出售，还是别的什么？
4. 按优先顺序，最重要的任务是什么？
5. 哪些功能与现代化事项最重要？

以下每项判断都出自作者本人；凡仓库自身记录与此不一致之处，文中都会指出。不迎合：现有文档中最薄弱的论断在 §4 中被点名。

---

## 1. 先说结论

**不要放弃这个项目。但要改变它的叙事框架。**

工程资产稀有而真实：一个 14.7 万行的 Objective-C 代码库，其无头引擎——SQL 生成、可移植存储、结果表类簇、两个线协议驱动——**已经在 Linux 上编译、测试并运行**，连接真实的 MySQL 与 SQL Server，Linux 侧约 1,200 个测试、iOS 侧约 2,000 个测试全部通过，文档写入器和七种导出格式的跨平台输出逐字节一致。极少有单人构建的系统能达到这一状态；几乎没有系统能在具备这种文档纪律的同时做到。把它丢掉将是真正的损失。

必须改变的是品类层面的雄心。把“世界级 BI 平台”理解为*与 Power BI、Tableau、Looker、Metabase 和 Superset 竞争*，对一名开发者加一对 AI 而言并不现实，因为这个市场由拥有数百名工程师和销售团队的公司主导（仅 Power BI 就占据约 27% 的品类份额；开源那一块已由 Metabase 和 Superset 服务得很好）。目标的诚实版本是：

> **在一个既有厂商在结构上无法占据的细分领域做到世界级：可移植、本地部署、可嵌入的报表，其产物——`.mad`——是一个 80 KB、可 diff、可纳入 git、确定性的文件，能在手机、笔记本电脑和服务器上运行，在任何地方渲染结果都相同，而其数据层是任何能返回表的东西——数据库、Web 服务、用户自己的服务器。**

这个细分领域是真实的、尚无人认领的，而这个代码库比市场上任何其他东西都更接近它（§6）。`MAD_FUTURE.md` 中的计划已经描述了它；那份文档所说的“一种运行在手机、笔记本电脑和服务器上、自带呈现的模型格式”，正是这个定位。`MAD_FUTURE.md` 所缺少的、也是本报告所补充的，是排序纪律：项目当前的轨迹是**处在客户的上游**，而最大的单一风险不是技术失败，而是又一年卓越的基础设施建设却毫无外部信号。

## 2. 项目实况：量化审视

### 2.1 仓库

- 4,792 次提交，首次提交于 2012-01-02——一个 14 年历史的代码库，单一作者。
- 活动模式：2015–2017 年密集（最初的构建期），2018–2024 年近乎休眠（5 年内约 30 次提交），2024-07 复苏（v9.0，“重返 App Store”），随后从 2026-09 开始转型：**仅 2026 年 10 月就有 298 次提交**，几乎全部是智能体辅助、测试先行的功能工作（Linux 移植、导出接缝、条码重新整合、SQL 录入——`TASKS.md` §7–§16）。
- 13 个框架加应用共约 147,000 行自有源代码（仅 `MADDesigner` 就有 6.3 万行）；约 62,000 行测试代码。

## 3. 真正的资产——这个项目拥有而竞争对手没有的东西

这些是后续每项建议的核心支撑论断。全部五项都是*实测的*，而非愿景。

1. **引擎今天就能在 Linux 上连接真实数据库运行。** `MAD_LINUX.md` §9（阶段 D）中设定的诚实 go/no-go 于 2026-10-16 被满足并通过：`mad` 在镜像中构建，经网络从 MySQL 8.4 刷新 50 行、从 SQL Server 2022 刷新 20 行，两个实时测试套件在容器内通过。本可能扼杀 Web 目标的工具链风险——GNUstep 上的 Objective-C——已由 123 个全部通过的测试可执行文件消除，而不是靠希望。剩余风险是小众工具链的*维护*（§12），而不是*它能否工作*。

2. **逐字节一致、跨平台、确定性的输出。** 同一个 `.mad` 在两个平台上写出相同的字节；`json`、`csv`、`text`、`html`、`html-flow` 和 `json-report` 导出在摘要上完全一致。这是这个代码库最不寻常的属性——它意味着格式是*可规格化的*、渲染器是*可测试的*，而这恰是开放规范（§8）和嵌入式 OEM 方案（§6.2）所需的证明。

3. **`.mad` 格式是真正的产品产物。** 一个可移植容器（带 v1 魔术头的 bzip2-tar）、一套有文档的 SQLite 存储架构，以及格式有文档的伴随文件（`MAD_FORMAT.md` §5）。报表即代码（reports-as-code）——dbt 这一代用 YAML 换来的属性，但附带呈现，且无需服务器。

4. **测试纪律。** 12 个套件中共约 2,000 个 iOS 测试方法（仅 MAD 就有 696 个），123 个 Linux 可执行文件 / 约 1,200 个测试，连接实时数据库的套件在不可达时跳过而非失败，黄金 SQL 测试，往返测试夹具，以及摄取路径上的基准测试。这是护城河的地基：每一项对外主张（可移植性、确定性、正确性）都是可执行的，而非口头断言。

5. **文档。** `MAD_FORMAT.md`、`MAD_DATA_OBJECT.md`、`MAD_LINUX.md`、`ROADMAP.md`、`TASKS.md`、`BUGS.md` 等文件构成了作者所见过的、同等规模下文档最完善的单人项目。这些文档不是额外负担；它们是销售材料和 AI 可辅助性的基础（§11.5）。

6. **智能体工作流本身。** 2026 年 10 月的速度——三周内四个实质性功能，每个都测试先行、以合并为门禁——证明了一名开发者加上 Claude Code 能以小团队的速度交付。这是整个计划所依赖的规模化机制，值得明确说明：战略*不是*“单打独斗的开发者对抗 BI 行业”，而是“一名开发者带着 10 倍力量倍增器对抗一个细分领域”。

7. **平台已有一半成真，而不只是承诺。** 项目简介中提到的可扩展性——新的数据库类型（继承 `MADDatabase`）、新的导出格式、新的元素类型——如今已有前两者的注册表，以及第三者的可用示例（条码元素）。因为驱动的契约是*“以表的形式返回架构和行”*，而执行接缝的类型是 `id <MADDataTableWriting>`（`MAD_DATA_OBJECT.md` §3.3），所以驱动可以面向任何能被做成表的东西：Web 2.0 REST 服务、用户自己的服务器、一个文件。这就是一句话讲完的平台故事，它改变了市场定位（§6）：这不是“面向 MySQL/SQL Server 用户的 BI”，而是一个数据层可插拔的报表平台。承诺与平台之间唯一的缺口在 §4.7 中被点名。

## 4. 诚实的负债

### 4.1 已发布的产品被项目自己评为最高优先级的缺陷所阻塞

`TASKS.md` §1：创建文档时出现两次钥匙串提示，用户的原话是——*“这个钥匙串流程似乎必须做对，否则没人会真正使用这款软件。”* **它从 2026 年 9 月之前就一直未解决，而最近三周的工作却投向了条码和 SQL 录入。** 近期的工作没有白费——但这种排序印证了 §1 中点名的模式：项目倾向于深入、有成就感、上游的问题，而回避小而枯燥、面向客户的问题。这是本次分析中最重要的行为学发现。修复它需要的是一次决策加少量代码（`TASKS.md` §1 点出了设计问题：使用平台 AutoFill 还是应用自有的钥匙串条目）；§4 中的测试已经指定。

### 4.2 没有分发渠道，没有可发现性，没有收入路径

- 在网页搜索中以“MAD Designer”找不到 App Store 上架页——这个名字与 MIDI Designer 以及泛泛的“MAD”噪音相撞，应用没有任何方面能浮现出来。无论 v9.0 的安装基数是多少，它都不可被发现，这使得它作为渠道在今天几乎为零。
- 应用内没有变现（`TODO.md`：“添加商店 / 变现路径”属于次要事项），文档中也没有任何定价。
- 产品**不出售**，也没有美国客户群（用户于 2026-10-22 确认）。存在的积极信号是定性的：用户曾把软件展示给一些人，它对他们确实有用。这是对核心闭环——连接、查询、设计、查看——真实的早期验证，也是 §6.2 中招募设计合作伙伴的种子；它不是收入，不是渠道，也还不是市场。

### 4.3 引擎覆盖两个数据源；市场说的是三个

MySQL、SQL Server、SQLite。**没有 PostgreSQL**——而它是整个开源/自托管 BI 受众的默认选择（Superset 本身就要求 Postgres；Metabase 的社区版运行在它上面）。`TODO.md` 正确地把“所有其他数据源”列为雄心，但 Postgres 不是“另一个数据源”——它是*那个*可服务市场的杠杆。一个驱动（而且注册表让它成为一个可增量的框架，而非核心改动）大约能让引擎可服务的市场翻倍，而且它是证明项目简介中的可扩展性承诺真实存在的最廉价方式。

### 4.4 与买家见过的任何 BI 工具相比的产品差距

- **报表中没有图表。** 查询可视化画布存在；报表元素是标签、数据标签、聚合、条码、图像。每个竞争对手的首屏都有图表。`TODO.md` 把“图表类型”列为未来事项。这是产品中最大的单项对等差距。
- **没有仪表板**（多报表组合），也**没有运行时参数**（不编辑设计即可刷新“截至上个月”的数据）。两者在存储模型或任何设计文档中都不存在。
- **没有计划任务/投递**——经典的 BI 楔子（“周一早上 7 点把 PDF 邮件发给我”）是一个服务器端功能，而 CLI 的形态已经完成了 90%。
- 独立查看器 target 无法链接（`ROADMAP.md` §2.1），而它应该是什么，是一个尚未做出的产品决策。
- UI 测试实际上已失效（XCUITest 环境看到的是空的无障碍树——`TASKS.md` §16 阶段 D 记录的缺口）。

### 4.5 Web 产品缺失的 80% 不是引擎

`MAD_FUTURE.md` §4.1 说得对，引擎已经可以在没有 UI 的情况下运行；其 §5.2 的清单是对代码库中**根本不存在**之物的诚实编目：身份、组织、角色、ACL、凭据保险库、许可/计费、计划任务、审计、带密钥与作用域的 API 表面。其中每一项都是智能体可以协助构建、但任何工程上的优雅都无法替代的产品工作。多租户 Web 产品不是“带 HTTP 的 CLI”——它是围绕 CLI 的平台。§7 对此做了排序，使平台在外部信号存在**之后**构建，而不是之前。

### 4.6 许可证卫生是真实且未完成的

`TASKS.md` §10 / `LICENSE_COMPLIANCE_PLAN.md`：`mysqlclient` 8.4.10 是 GPLv2——这对任何专有二进制都是发布阻塞项，包括 Linux 运行时镜像，**在其被分发的时刻**即成立；三个已提交的组件完全没有许可证授予（Karl Kraft MySQL 连接器、`NSData+AES256`、`NSOperation+Advanced`）。它们都被点名，都有替换计划，但没有一项完成。这一切都不阻塞*开发*；但全部阻塞服务端的*发布或公开*。MariaDB Connector/C 替换是唯一一项真正的工作量（27 个 `mysql_*` 入口点，相同的 C API）。

### 4.7 “任何能返回表的东西”的承诺有一个真实的漏洞

可扩展性的故事在执行层是属实的——`MADDatabase` 的抽象接缝是 `executeSQL:fieldKeys:onConnection:intoResultTable:withError:`，目标是任何可写的表——但*编译*层是共享的：`MADQueryFull` 把查询图编译成每个驱动一段 SQL 文本（`MAD_DATA_OBJECT.md` §3.2）。对 REST 或 Web 2.0 驱动而言，自然的输入是图（表、字段、谓词、分组），而不是 SQL 文本；这样的驱动今天必须从交给它的字符串中把 SQL 反解析出来。解决办法是每驱动的编译钩子——与用户 2012 年为 Salesforce SFQL 在 `TODO.md` 中勾勒的形状相同——它属于引擎契约阶段（阶段 1，§7.2），这样服务器产品中的“安装一个驱动”才意味着“为任何东西安装驱动”，而不是“为恰好匹配我们方言的 SQL 数据库安装驱动”。

对服务器而言还有一个较小的后果：**用户安装的驱动就是服务器进程中的任意代码。** 注册表的 `+load` 注册和 Linux 的 whole-archive 链接（`MAD_LINUX.md` §9 阶段 D）适用于受信任的第一方驱动。驱动市场（`MAD_FUTURE.md` §8.3）在存在之前，必须先回答插件信任问题——签名、沙箱，或在 CLI 边界上把驱动放在隔离的工作进程中运行。这是阶段 4 的关切，但必须从一开始就设计进 API，而不是在驱动已安装到生产环境之后才补上。

## 5. 市场现实（2026）

以下论断来自为本报告所做的研究；来源列于文末。

- **BI 已经整合。** Power BI（约 27% 份额）和 Tableau（约 18%）占据主导；整合趋势是分析*嵌入其他应用*，而非独立工具。对新进入者而言，独立的 BI 是红海。
- **开源/自托管 BI 已被服务。** Metabase（AGPL 开放核心，云服务入门约每月 $85–100，嵌入式 React SDK 是一项真实业务）和 Superset（Apache-2.0，由 Preset 作为商业赞助方）已经占据了“自托管 BI”，两者都有真实的运维负担（Postgres + Redis + workers）和真实的功能缺口（Metabase 的治理在付费层；Superset 的可用性偏技术）。两者都是*绑定服务器、仪表板形态*：都不产出一个可移植、可 diff、可嵌入的报表产物。那就是裂缝。
- **嵌入式分析是一个巨大而真实的市场**——2026 年的估计在 110 亿至 910 亿美元之间，取决于机构的定义，全都指向增长——由 OEM 厂商（Telerik、Stimulsoft、Logi）服务，其模式是 ISV 把报表嵌入自己的产品。`.mad` + CLI + 引擎在形态上*就是*一套 OEM SDK。这个市场缺少的成分是销售渠道，所以 §6.2 推荐的是无需从零构建渠道的那条路线。
- **移动 BI 是一个真实的小众市场，且有真实的趋势**——67% 的企业认为移动分析访问很重要，该细分市场的预测复合年增长率约为 21%，而领导者的移动应用（Power BI Mobile、Tableau Mobile）是伴随应用，而非设计器。移动优先的新进入者（Anywhere BI、Zing Data，均为 2026 年）证明了需求，也证明了竞争威胁：AI 原生的移动 BI 正在成形，而这个项目完全没有 Web 存在。
- **报表即代码是一种受尊重且正在成长的亚文化**（dbt 的模式——可移植、可版本化的定义，重活由一个引擎承担）——而这正是这个代码库的架构，只是多了一样 dbt 所缺少的东西：附带呈现。

诚实的解读是：市场对*又一个 BI 工具*充满敌意，而对*一个附带引擎的可移植报表产物*在结构上无人占据。

## 6. 价值场景，如实排序

### 6.1 App Store（继续做；但它不是生意本身）

现实的结果：低收入、低风险。iPad 上的移动 BI *设计*是一个专业消费者的小众市场，而产品**目前不出售——App Store 上架已失效，续订开发者账户在等待资金**（2026-10-24）。因此这里的第一个变现里程碑是*续订并*重新上架（免费查看器、付费设计器，或者干脆全付费），而不是优化价格。这个场景**不**作为开源发布的门禁（附录 A）：App Store 受众与开源受众几乎不重叠，应用会作为后面的章节回归——续订、修复钥匙串缺陷（§9）、发布——届时它是对一个已经存在的社区的一次小宣布。应用的最终角色是**旗舰和广告牌**：一个潜在的 OEM 合作伙伴或设计客户可以触摸的演示。免费增值的查看器 + 付费设计器，低定价（一次性 $10–20 或每月 $2–3），是符合该天花板的模式；把收入当作获取线索的手段，而非收入本身。

### 6.2 嵌入式 / OEM 许可（与技术的契合度最高；首笔收入最慢）

引擎、`.mad` 格式、CLI 和导出格式合在一起*就是*一套面向 ISV 的 SDK，这些 ISV 需要在自家产品内部提供自助报表——即 Telerik/Stimulsoft 的模式，只是规模更小、表面更聚焦：“你客户的报表是一个可移植文件，由你的应用通过我们的引擎渲染。” 驱动接缝让这个方案比固定数据源的引擎更强：ISV 可以用驱动面向*自己*产品的数据——“你客户的报表通过你编写的驱动来查询你平台的数据”——这正是“任何能返回表的东西”的承诺穿上了一份契约。对一名开发者而言，现实的路线**不是**建立 OEM 销售组织——而是 1–3 个设计合作伙伴 ISV（拥有 SQL Server/MySQL 资产的垂直 SaaS：ERP、现场服务、事务所管理），通过内容营销和开放引擎（§8）主动找上门，采用收入分成或年度许可条款。预期结果：一年或更长时间收入为 $0，然后是黏性强、高毛利的许可收入；或者来自恰好与本品互补的嵌入式分析厂商的收购兴趣。

### 6.3 开放核心的自托管服务器（战略方向；dbt/Metabase 模式）

开放格式规范和引擎；保留设计器应用和服务器为付费。这是“世界级”对一名单人开发者还有任何可信路径的唯一场景：可移植产物像 dbt 模型和 Metabase 仪表板那样在数据/分析工程社区中传播，而商业产品是自托管者最终会购买的*托管/企业*层（计划任务、保险库、ACL、审计——`MAD_FUTURE.md` §5.2 的清单）。用户可安装的驱动补全了这幅图景：服务器产品变成一个平台，客户可以扩展其数据层（为内部服务、Web API、文件编写驱动）——与养大 Metabase 的同一个插件飞轮——一旦生态存在，驱动市场（`MAD_FUTURE.md` §8.3）就是自然的第三条收入线。预期结果：12–24 个月收入近乎为零，同时产物寻找它的社区，然后要么是一个小而持久的生意，要么是一个强势的收购位置。许可证卫生工作（§4.6）是*前提*，而且已经列入计划。

### 6.4 封闭格式的企业出售（不建议）

在没有销售团队、品牌或社区的情况下，用封闭格式的专有 BI 服务器去对抗 Metabase/Superset/Power BI，是胜算最差的场景。封闭格式买来的护城河，在有人想要这个格式之前一文不值，而没人会听说过它。唯一*真正*值钱的封闭之物是设计器体验——保持它专有。

### 6.5 放弃——不是现在，但有明确的判据

§3 中的资产太强，持有成本太低，只要工作还令人愉快就不该放弃。但这个诚实的终局问题应当被排上日程，而不是无限延后：**如果到 2027 年底仍没有外部信号**（没有付费用户、没有 OEM 设计合作伙伴、开放引擎上没有有意义的社区牵引力），那么项目的价值就只是作品集和热情——一个正当的结果，届时把一切都开源就是终局的价值玩法，而不是失败。§12 精确地陈述了这个触发条件。

## 7. Web 前端：现状与具体计划

### 7.1 一段话讲现状

Web 目标中困难的 80% 已经完成：引擎在 Linux 上无头运行，连接真实数据库，有运行时 Docker 镜像和逐字节一致的导出。剩下的是 (a) 引擎周围的产品平台——一项都不存在——以及 (b) 浏览器 UI——一项都不存在。因此最廉价、信号最强的 Web 产物**不是** `MAD_FUTURE.md` §4.3 描述为终态的那个完整克隆；而是一个建立在已存在产物之上的*查看器服务器*（`json`、`html`、`html-flow` 已经是 API 载荷），完整的三标签页克隆则是长期目标。

### 7.2 分阶段计划

**阶段 0——卫生与业务分叉（数周，主要是决策）。**
- 修复钥匙串/凭据流程（`TASKS.md` §1–4）——已发布产品的阻塞项。
- 做出开放/封闭的决策（§8）——它改变许可证工作和营销。
- MariaDB Connector/C 替换 + 三个无许可证重写（`LICENSE_COMPLIANCE_PLAN.md` §3）——在*发布*镜像或任何服务器二进制之前必须完成。
- 对渲染缓存键做内容哈希（`MAD_FORMAT.md` §8.4）——一个已知的过期页面机制，不能被为众多客户端渲染的服务器继承。

**阶段 1——引擎契约（`MAD_DATA_OBJECT.md` 阶段 1–2）。**
把 SELECT 列表的构建与执行分开；加入 describe/execute 协议；让查询自己拥有自己（退役 `MAD_DATA_OBJECT.md` §3.6 中点名的三个硬编码点）。不改存储，不改 UI，可由现有测试套件证明。这正是把“CLI 的动词”变成“服务器的 API”的一步——该文档自己的 §6 恰恰提出了这一点：CLI 是引擎的*客户端*，而入口点是缺失的一块。是数周，不是数月。

**阶段 2——MAD Server v0（查看器服务器）。**
在 `mad` 前面的一层薄服务（`MAD_LINUX.md` §2 已经推荐的子进程形态，或者如果经实测确实重要，也可以是一个小的链接式守护进程）：一个文档目录、放在简单队列后面的 `refresh`，以及把 `html`/`html-flow`/`json` 提供给浏览器的 `export`。**先做单用户**——没有组织、没有 ACL、没有计费；那些属于阶段 4，并且以外部信号为门禁。Linux PDF 继续延后（`MAD_PDF_LINUX.md`）：对 HTML 仿真件的浏览器打印覆盖了所有面向人的场景；只有无人值守的服务器 PDF 才需要那个写入器。

**阶段 3——Web 查看器 UI。**
文件列表、分页查看器、刷新按钮、导出。这是最低限度的面向产品的 Web 产物；因为服务器已经在提供载荷，这项工作只需数周到数月。这也是可以向设计合作伙伴或 OEM 潜在客户展示的产物。

**阶段 4——平台层——只有在信号之后。**
身份、组织、角色、ACL、保险库、计划任务、计量（`MAD_FUTURE.md` §5.2）。这是整个计划中最大的一块新产品表面，而在任何人提出需求之前就构建它，是现有代价最高的错误。`MAD_FUTURE.md` §5.2 自己的架构说明是对的：所有这些都附着在 CLI 边界*周围*——这正是它可以等待的原因。

**阶段 5——Web 设计器，逐个标签页。**
先做查询标签页（差异化所在），设计器画布最后（最昂贵的 UI 工作——一个 Figma 形态的画布需要数月）。与 iOS 应用功能对等是*愿景*；它不能成为 MVP 的门槛。

**并行轨道——Postgres 驱动。** 唯一一项具有不成比例市场效应的引擎侧投资（§4.3）；也是引擎开放时对可扩展性承诺最干净的公开证明。

### 7.3 macOS 与 Windows 的诚实定位

- **macOS 很近、很便宜，而且不是绕路。** 应用已经发布“My Mac (Designed for iPad)”版本（`CLAUDE.md`），所以 Mac 存在今天就有。下一个有意义的 Mac 步骤是一个*原生* macOS `mad`（不必折腾模拟器）：每个随附库的 macOS 切片都已经能构建（Compressor 阶段 4–5），唯一剩下的阻塞是 `MADFoundation` 四个已归类的文件中的 UIKit import（`ROADMAP.md` §2.1 第三个要点）——与 Linux 已经证明过的同一种无头目标手术，只是平台更容易（Apple Foundation，没有 GNUstep）。超出 Designed-for-iPad 的原生 macOS *应用*是对 6.3 万行的 AppKit/Catalyst 重写，不值得；Web 客户端就是桌面应用。
- **Windows 靠服务满足，而不是移植。** 引擎运行在 Docker 中，而 Windows 原生托管 Docker；Web 客户端运行在浏览器中，而 Windows 有浏览器。原生 Win32 移植在证据上根本不可行：微软自己的 WinObjC 桥已于 2025 年归档（`MAD_LINUX.md` §6），而格式文档的“Windows 上的读取器”义务（`MAD_FORMAT.md` §7）在原生移植之前很久就可以由一个浏览器/SQLite-WASM 读取器满足。Windows 是 Web 产品的*部署目标*，永远不是移植。

## 8. 开放还是封闭？——分叉，附建议

`MAD_FUTURE.md` §8 在这个分叉上未作决定（“格式是否开放？”），其 §10.4 说要在规范发布*之前*决定。本报告的建议：

- **开放格式规范**（`MAD_FORMAT.md` 几乎可以原样发布）。一份已发布、带版本的规范是会复利的营销，送出去不花分文——而且是 OEM 故事（§6.2）与报表即代码社区（§5）都需要的公信力。
- **以宽松许可证（Apache-2.0）开放引擎和 CLI**，在阶段 0 的许可证卫生完成之后。引擎的*存在*就是卖点；把它送出去，是单人开发者否则买不到的分发渠道。开放核心的经济学（Metabase：AGPL 核心、付费企业层）恰恰在这个市场里被证明过。
- **保持专有：MAD Designer 应用**（设计器体验是封闭护城河真正保护的唯一东西）**以及服务器的平台层**（阶段 4 清单——保险库、ACL、计划任务、审计——正是自托管者付费购买的东西）。

这就是 dbt/Metabase/Superset 模式，应用到一个许可证状态已经过审计、测试纪律能为规范的每一项主张背书的代码库上。替代方案——全部封闭——把生态的上限压在一个人销售能力的水平上，而这正是整个项目的约束瓶颈。

## 9. 最重要的任务，按顺序

1. **钥匙串/凭据流程（`TASKS.md` §1–4）。** 用户自己的话表明它阻塞了产品。它是一次决策，加上几天工作，加上已经指定好的测试。现在就做——在任何进一步的上游工作之前——因为它的持续拖延是 §1 风险模式最清晰的证据。
2. **开放/封闭决策（§8）。** 一个业务决策，不是代码；它约束着许可证工作和每一件营销。
3. **许可证卫生（`TASKS.md` §10）。** MariaDB 替换 + 三个重写。是 Linux 镜像和任何服务器二进制发布的先决条件；计划已经存在（`LICENSE_COMPLIANCE_PLAN.md` §3）；这是诚实的机械工作，背后有真实的测试。
4. **引擎契约（`MAD_DATA_OBJECT.md` 阶段 1–2），加上每驱动的编译钩子（§4.7）。** 服务器 API 形态的前提；没有行为变化；数周。这个钩子很小，但它使“安装一个驱动”意味着*任何东西*，而不只是又一种 SQL 方言。
5. **查看器服务器 + Web 查看器（阶段 2–3）。** 第一个有面孔的 Web 产物。
6. **Postgres 驱动（并行）。** 市场杠杆。
7. **报表级图表。** 与买家见过的每一种 BI 工具相比最大的单项产品对等差距；元素接缝（`ROADMAP.md` §5.3，目前仍只有设计）是载体。
8. **格式化器性能（`TASKS.md` §14.1）。** 逐行的页面索引拷贝是一个真实的 O(rows²/page) 缺陷；在服务器渲染大型报表之前修复。
9. **独立查看器的决策。** 修复或删除它；正如 `MAD_FUTURE.md` §8.1 所指出的，它是免费增值 App Store 模式中天然的免费客户端。
10. **队列中的其他一切**（警告清理 §13、SYBDATETIME4、MADFileManager 事项、SQL 录入阶段 E、Linux PDF 写入器）——真实的工作，但都不在通往价值的关键路径上。

## 10. 重要的功能与现代化——以及不重要的

**要做：**
- Postgres 驱动（市场）；图表（产品对等）；运行时参数（任何真正的报表产品都需要）；计划投递（楔子）；按照 `MAD_FUTURE.md` §7 的拒绝并修复模式进行 AI 报表构建（一个真正的差异化因素，架构已经为其成形——模型写图，引擎验证，而用户对智能体的熟练程度正是所需的技能）。
- 保留 Objective-C。**不要用 Swift 或 Python 重写。** Linux 检查点已经通过；双实现漂移风险（`MAD_LINUX.md` §2 的核心论点）是真实的，而重写的触发条件已经定义（§9 阶段 D 失败）。代码库的“老语言”不是负债；它是已经兑现的平台押注。
- 把**显示表面视为第四道接缝。** 渲染管线在设计上以打印为先——页数统计和分组分页，真正困难的部分——但一个“现代”显示（连续、响应式、可交互）不是 UI 重写；它是导出器旁边的*渲染器*。节布局和元素遍历已经是平台中立的（`MADReportPageBuilder` + `MADDocumentRenderDataSource`），`html-flow` 已经是第一个非页面形状的渲染，导出器注册表的形态原样适用。其中诚实的子任务：元素类型需要按表面区分的渲染契约（今天 `-drawInRect:` 是 UIKit 的，HTML 导出器只绘制文本框），所以现代显示和 Linux PDF 写入器共享同一份接缝工作。
- 完成警告清扫（`TASKS.md` §13，应用 + MAD）——廉价、机械，让分析器信号保持有意义。
- 重新考虑 CI。2026-10-17 反对 CI 的决定对概念验证是合理的；对一个双平台逐字节一致的产品则是错误的。一个 GitHub Actions 任务在每次推送时运行 `./Linux/build.sh --verify`，把“输出一致”从手动仪式变成门禁，代价只是几个小时的 YAML。iOS 套件保持其为模拟器任务不变。
- 在任何服务器渲染之前，对渲染缓存键做内容哈希（阶段 0）。
- 在现有的自由度内，让应用的死重现代化：`MTPaper`（约 70 个文件）是已知的一团乱麻，`MADFeedback` 未被使用，`Scrimpter` 处于搁置状态。按项目自己的规则，行为安全的清理是受欢迎的——但不要在上述第 1–3 项之前做。

**不要做：**
- 不要构建多数据源/子报表装置（`MAD_DATA_OBJECT.md` §5——刻意不排期；一旦一个产品交付，组合的故事会卖得更好）。
- 不要在外部信号之前构建阶段 4（平台层）——它是计划中代价最高的非受迫性失误。
- 不要在 Linux 上追求逐字节一致的 PDF（`MAD_PDF_LINUX.md` 已经说明了为什么不可能）；浏览器打印覆盖了人的需求，结构等价才是正确的标准。
- 不要在任何地方移植 UIKit（`MAD_LINUX.md` §6：连微软都放弃了这个想法）。
- 不要让仪表板、带参数的仪表板、数据仓库规模或 AI 吃掉路线图：产品的立场——“报表按人的规模来，而不是 PB 级扫描”——本身就是一项功能，而 `MAD_FUTURE.md` §6 已经说要保持它。

## 11. 几乎不花什么钱的营销点子

1. **文档即营销：发布格式规范。** `MAD_FORMAT.md` 已经完成了发布级规范的约 90%。“一份报表塞进 80 KB，跑在手机、笔记本电脑和服务器上，在任何地方渲染都逐字节一致”是 Show HN 级别的钩子，瞄准的是已经在为可移植、可 diff、引擎拥有的定义付费的 dbt/分析工程人群。
2. **把 CLI 当作演示。** 一条 Docker 单行命令（`docker run … mad inspect sample.mad`）比任何落地页都是更好的演示，而且它已经作为 `Linux/verify-cli.sh` 的测试夹具集存在。把镜像公开发布（在 MariaDB 替换之后），作为“试用引擎”的产物。
3. **修正名字。** “MAD Designer”不可搜索（§4.2），并且与一个 MIDI 应用相撞。服务器/开放引擎产品需要一个独特的、可搜索的名字；格式可以成为品牌（“.mad 报表”）。廉价、一次性、会复利。
4. **本地部署/隐私楔子。** “在你的数据所在之处运行的 BI——没有云出口，没有数据仓库副本。” 引擎今天确实在 iPad 上设备端运行；这是一个受监管行业（医疗、现场服务、制造业）会听进去、而 Power BI Mobile 不会讲的安全故事。
5. **有针对性的嵌入式方案。** 拥有 SQL Server/MySQL 资产的垂直 SaaS ISV：“在你的产品内部提供自助报表；你客户的报表是一个文件，不是一张截图。” 对前两家以设计合作伙伴条款；案例研究就是第二个客户的价码。
6. **AI 角度，稍后。** `MAD_FUTURE.md` §7 的循环（模型输出图 JSON，引擎验证，精确的错误，修复）是任何地方最强的 AI 报表架构之一，而用户已经是驾驭它的专家。移动 AI-BI 的新进入者（Anywhere BI、Zing Data）此刻正在验证需求；楔子是“一个只能构建它能验证的报表的 AI”。
7. **App Store 作为广告牌**（在钥匙串修复之后）：免费查看器、廉价设计器、以示例报表作为演示。预期收入很小；预期*角色*是 OEM 潜在客户的第一次接触。

## 12. 点名风险，以及放弃的触发条件

1. **上游陷阱（概率最高）。** 项目会永远改进基础设施——更多逐字节一致、更多格式工作、更多接缝——因为乐趣和可衡量的胜利都在那里，而钥匙串缺陷一直未解决，仓库之外从没有人看到产品。对策：§9 的第 1–3 项有日期，阶段 3（Web 查看器）在日历上有截止日期，而不是在队列里。
2. **小众工具链的巴士系数。** libobjc2 + GNUstep + CMake + Compressor 是一套世界上恰好只有一个人在有意维护的技术栈。如果用户停下，项目就停下；开放引擎（§8）也是缓解这一点的招募渠道。
3. **竞争响应。** 在嵌入式/报表即代码上的成功会招来 Metabase/Superset 的功能跟进（两者都已有嵌入 API）。护城河是可移植产物 + 确定性 + 本地部署的故事——真实，但单薄；开放规范的速度比保密更重要。
4. **许可证暴露。** 在 MariaDB 替换之前发布 Linux 镜像，会让 GPL 问题变成现实（§4.6）。阶段 0 将其关闭；在此之前不应发布任何服务端的东西。
5. **规模上限。** 两遍式全量拉取模型在设计上就封顶了数据规模。保持它（这是报表，不是数据仓库），并从第一天起就在服务器中设置快照上限（`MAD_FUTURE.md` §6 自己的约束）。
6. **放弃的触发条件，只说一次：** 到 2027 年底，如果以下任何一项都没有发生——一个付费用户、一个 OEM 设计合作伙伴、开放引擎上有意义的牵引力——就接受项目的终局价值是作品集与热情，把其余部分开源，并停止投入。不要更早：§3 中的资产太强，而接下来的 12 个月是对 §5 论题最廉价的检验。

| 问题 | 回答 |
|---|---|
| 放弃？ | 不。资产稀有且经过测量；持有成本低。2027 年底重新检验。 |

## 附录 A——开源操作手册（2026-10-23）

“我该开放什么、何时开放、如何开放”的实用答案。一名开发者，刚接触开源：这里的整个设计原则是*机制最少化*。

**一个仓库，全部开放，采用 MIT。** 公开仓库就是这个仓库，经清理（§A.4）：全部十三个框架、Compressor、`Linux/`、`CLI/`、应用、文档、测试。唯一永远保持私有的是未来的 **MAD Server 平台层**，它从第一天起就有自己的私有仓库——专有代码存放在那里，开放核心的界线画在那里，而不是穿过应用。现在**不要**拆成引擎+应用两个仓库：拆分是一项永久的税负（双份 CI、跨仓库版本管理、拆分的 PR），换来的回报却不确定。应用的源代码不是护城河——App Store 的位置和纪律才是——而一个开放的 iPad 设计器正是对项目想要的受众的免费营销。只有当应用将来需要封闭组件时，才可以重新考虑拆分。

**许可证：MIT。** 最易管理，对战略瞄准的嵌入式/OEM 买家最为宽松，也让私有服务器可以轻而易举地复用一切。如果希望有专利授权，就用 Apache-2.0（文本更多，对企业稍好）；**不要**用 GPL/AGPL——著佐权需要单人开发者并不具备的执法能力，而且会吓退 §6.2 所依赖的 ISV。`.mad` 格式作为免费规范发布，并附一行说明：名称不在代码许可证的覆盖范围内。

**仓库公开之前必须发生的事，按顺序：**

1. **许可证卫生**（`TASKS.md` §10）：MariaDB Connector/C 替换和三个无许可证重写（Karl Kraft 连接器、`NSOperation+Advanced`、`NSData+AES256`）。贡献者不会碰一个含有无许可证第三方代码的仓库——这对*他们*是法律风险，所以这才是真正的第一步。
2. **文件头：** 每个自有文件一行 SPDX（可脚本化的一遍，约 1,500 个文件；理想的智能体工作）。一个 `LICENSE` 文件（MIT 文本）；同时发布 `THIRD_PARTY_LICENSES.md` 和 FreeTDS 的 LGPL 声明。
3. **历史清理——必需，且已测量。** `.git` 有 683 MB：旧的随附树（`3rdPartyProjects/`、`Compressor/source/`、1,797 个遗留产物）仍在历史中。对那些路径做一遍 `git filter-repo`，把公开仓库收缩到自有代码，并从公开历史中移除旧的随附 GPL 源码——这是来源上的胜利，而不只是体积上的胜利。保留 14 年的自有历史；它是故事的一部分。确认 `TEST-DB-INFO.md` / `run.log` 从未进入历史（已于 2026-10-23 检查：干净），并 grep 任何像凭据的东西。
4. **CI，因为公开会改变无 CI 的决定。** 一个 GitHub Actions 任务在每次推送时运行 `./Linux/build.sh --verify`，在 README 中挂一个绿色徽章。一个没有 CI 的开放仓库，在发布之前就会显得已被遗弃。（在 macOS runner 上跑 iOS 套件的任务可以稍后再加。）
5. **公开表面：** 围绕下面的推介重写 README（现在只有五行）；`CONTRIBUTING.md` 写明构建命令和项目的测试先行规则；`SECURITY.md`；`CODE_OF_CONDUCT`；议题模板（缺陷、驱动提案）；PR 模板；用 DCO 签署代替 CLA。
6. **名字，在发布前决定**（§11.3）——社区形成之后再改名很痛苦，而“MAD Designer”不可搜索。
7. 可选但廉价：在切换之前让律师瞄一眼 `LICENSE_COMPLIANCE_PLAN.md`。

**给出去的东西。** 是的——一次开源发布需要一个给出去的东西，而它**不是** Web 产品。给出去的是三件已经存在的产物：(1) 已发布的格式规范（`MAD_FORMAT.md` 作为文档站点），(2) 可运行的引擎——一条 `docker run … mad inspect London.mad` 命令加上示例文档，以镜像形式发布（在第 1 项之后），以及 (3) 证明——跨平台逐字节一致的输出、123 个通过的 Linux 测试、14 年的历史。App Store 应用**不是**发布的一部分：上架已失效，其续订在等待资金（2026-10-24），而且两个受众几乎不重叠。它会作为后面的章节回归——续订、修复钥匙串缺陷、发布——作为对届时已经存在的社区的一次自己的宣布。一句话讲完推介：**“报表就是一个文件。”**

**何时。** 第 1–6 项一落地就做——大约 3–6 周的兼职工作。不等 Web 设计器的两个理由：发布是一次性的（Show HN 只有一次机会），而且故事已经很利落；在 Web 版本*之前*开放，意味着社区可以帮忙构建它，而这正是分担负担的动机本身。现实顺序：卫生 → 文件头/清理 → CI + 公开表面 → 发布 → 然后是驱动教程和 Web 服务器，作为社区可见的工作。

**社区，附诚实的算术。** 开源不会创造社区；采用才会，而采用在发布之后数月才到来。头几个月零贡献者是正常的曲线。这个项目特有的飞轮是**驱动编写教程**（“一个下午写出一个 MAD 驱动”——接缝已经是真实的）：每个驱动都是一项扩展平台的贡献，而 Postgres 驱动是旗舰示例——要么公开构建，要么标记为一等公民级别的首个贡献。持续的工作：回复每一个议题、每月发布新版本、保持 GitHub Discussions 开放。发布阵地：Show HN、r/selfhosted、r/dataengineering、dbt 社区、面向企业角度的 LinkedIn。要持有的预期：开源的直接回报是分发和入站兴趣（OEM 询盘、设计合作伙伴）；分担开发负担是 6–12 个月以上的红利，而不是发布当天的红利。
