# Porting a file into MAD's headless engine

The headless engine is the same Objective-C source compiled three ways: Apple
(frameworks), Linux (GNUstep + Clang), and Windows (GNUstep + MSVC Clang). A
file that compiles on Apple can still fail in the Linux image or on Windows.
The usual causes are five:

1. It is missing from one of the two source inventories.
2. It imports a UI framework without a guard.
3. An import's case does not match the file name.
4. It depends on a compat shim that exists on one platform only.
5. A category is dropped because its archive was not whole-archived.

## The 12 headless frameworks

`MADFoundation`, `MADDataStructures`, `MADCocoaExtensions`, `MADFileManager`,
`MADAPI`, `MADSqlite3`, `MADTds`, `MADTdsClient`, `MADMySQL`, `MADPostgres`,
`MADBarcodes`, `MAD`.

Not headless: `MADExplorer` (UIKit), `MADFeedback` (unmaintained). The app
targets — `MADDesigner` (iOS), `Mac` (AppKit), `Windows/App` (WPF over the
`mad serve` process) — are separate and are not in these inventories.

## 1. Add the file to both inventories, or exclude it with a reason

Each headless framework has one inventory per build:

- `Linux/cmake/<Framework>Sources.cmake`
- `Windows/Engine/cmake/<Framework>Sources.cmake`

The implementation file lists must name the **same files**. Only the comments
may differ — they carry the per-platform exclusion reasons. `Linux/CMakeLists.txt`
reads the Linux lists; `Windows/Engine/build.ps1` reads the Windows lists.

After editing either side, run the read-only parity check:

```sh
python3 -I scripts/dev/check_source_lists.py
```

An exclusion is a decision, not an omission: name the file under a group (the UI
tail, the keychain, the document class) with a one-line reason, the way
`Linux/cmake/MADSources.cmake` does.

The file is shared source, not a headless-only copy: add it to the framework's
Xcode target too (a Public header if it is exposed as `<Framework/Header.h>`).

## 2. Decide whether the file is portable

A view, renderer, or `UIFont`/`UIImage` holder is not portable. Neither is a
`UIDocument` subclass, `UIBezierPath` drawing, `UICollectionViewLayoutAttributes`,
or a `UIApplication` background-task helper. Exclude it, or guard the Apple
part.

Use `#if __APPLE__` for a source guard. Do **not** use `TARGET_OS_*`: GNUstep
does not define it. Comment what the Apple branch does, so the next reader does
not have to guess.

Prefer a compat shim before a source guard. `Linux/Compat/` and
`Windows/Engine/Compat/` mirror each other; when a Linux shim changes, port the
change to the Windows copy or record why it does not apply.

## 3. Make imports self-contained and case-exact

The headless prelude supplies only the compat shims, so every header and source
must import what it uses. Compile each header as its own one-line translation
unit when in doubt; every failure names a missing import. The recipe is in
`Linux/AGENTS.md` ("Adding the next framework", step 4).

Case matters: the Mac's filesystem is case-insensitive, the Linux image's is
not. `#import <MAD/Foo.h>` compiles on the Mac and is a fatal error for a file
named `foo.h`. Check every `<Framework/Name>` import against the real header
names.

### Header resolution — the "same directory" trap

The headless build has no Xcode header map. A framework header is reachable by
two routes, and "same directory" only covers one of them:

- a quoted sibling import, `#import "MADNewThing.h"`;
- a framework-qualified angle import, `#import <Framework/MADNewThing.h>`,
  through the shim. The only include roots a framework target gets are
  `$SHIM_DIR` and `Linux/Compat` (tests also `Tests/Support`). A flat
  `<MADNewThing.h>` cannot resolve.

For ten frameworks the shim is one symlink to the source directory. `MAD` and
`MADBarcodes` use a *directory of per-header symlinks* generated by
`file(GLOB ...)` at **configure** time. A header added since the last configure
has no link, and a header in a new subdirectory is never globbed; both need a
reconfigure, and a new subdirectory also needs
`target_include_directories(mad PRIVATE ...)` and the Windows directory list.
The Windows shim refreshes its copies every run, so a header can work on Windows
and fail on Linux until the Linux configure is re-run.

Headers are never listed in the source inventories (implementation files only),
so a missing header is never a parity failure. The decisive diagnostic is the
one-line translation-unit compile from `Linux/AGENTS.md`, with `-H`/`-v` to
print the include search path.

## 4. Respect linkage

Framework archives link whole-archive so categories survive — Apple's `-ObjC`
does the same job. The driver archives are whole-archived from `mad` because a
driver's work is its categories. A framework archive that is *not*
whole-archived links silently without its categories; that is a crash at the
first message send, not a warning. The compat shims are one archive,
`madcompat`, shared by every executable.

## 5. Port the test and register it

- Port the Xcode suite to `Linux/Tests/` and `Windows/Engine/Tests/`, one
  executable per suite, using `MADTestSupport.h` (`MAD_PASS`, `MAD_PASS_EQUAL`,
  `MAD_NEED`, `MAD_SKIP`).
- Register it in `Linux/CMakeLists.txt` (`mad_add_framework`) and
  `Windows/Engine/build.ps1`.
- Tests compile with MRC (`-fno-objc-arc`); the framework stays ARC. An
  object-typed `__block` capture must `retain` explicitly.
- A GNUstep divergence is fixed, recorded as a `MAD_NEED` with a reason, or
  asserted per-platform — never silently skipped. Skips are counted separately
  and are not needs.
- Two suites that share a fixture or the per-user state directory need a
  `RESOURCE_LOCK` in `CMakeLists.txt`; without it they race intermittently.

## Verify in the right order

1. **Fast, compiles the new source:** build the touched target in the existing
   image (per-target `docker run`; `Linux/AGENTS.md` "Conventions and hazards").
2. **Fast, read-only:** `python3 -I scripts/dev/check_source_lists.py`.
3. **Full, once before the PR:** `./Linux/build.sh`. The Dockerfile copies the
   tree at build time, so this is the first command that compiles the edit into
   the image. `./Linux/build.sh --test` alone re-runs the old binaries.
4. **Windows:** `pwsh -File .\Windows\Engine\build.ps1` on the elevated
   workstation (`-SkipToolchain` once the toolchain exists; `-Clean` after
   header or directory changes), then
   `dotnet test Windows/App/Mad.Designer.Windows.slnx`. The hosted runner
   downloads a prebuilt engine; the engine build is not a routine local check.
5. **Apple regression:** run the touched framework's iOS suite. The iOS suite is
   the arbiter of the platform guards this port adds.

## Do not

- Edit only one inventory.
- Add a file to an inventory without porting its test.
- Use `TARGET_OS_*`.
- Rely on the Mac's case-insensitive filesystem.
- Run the full Linux build after every edit; use the per-target proof and save
  the full gate for the PR.
